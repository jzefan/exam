# 学习通教师阅卷功能移植分析

日期：2026-09-20。依据 ArkLoop 与 exam 当前工作区源码，并按用户最新确认的范围修订。本文保留整体设计；第一阶段连接验证代码已实现，当前进度和启动步骤见 [学习通连接验证](../chaoxing-connection.md)。评分与数据库迁移尚未实现。

## 1. 已确认范围与建议结论

本阶段只服务教师批改评分：连接学习通 → 获取课程和考试 → 获取考生姓名、学号与答卷 → 大模型评分 → 教师复核 → 结果保存在本系统并支持导出。结果不回填学习通。

考生是某场考试中的一条记录，不创建或绑定本系统学生账号，不建立跨考试学生档案，不接入学生错题本、补练、学生通知或本地考试作答流程。课程、班级也不需要先映射为本系统教学管理对象。

最新产品约束：教师不接受桌面客户端，优先网页免安装，只有免安装路径不可用时才考虑浏览器扩展。推荐先验证服务端浏览器登录和采集，再复用 ArkLoop 解析器及本系统评分引擎，新增“学习通阅卷”业务记录。无需将外部记录转换成 `User / ExamStudent / StudentExamSubmission`。

```text
教师登录本系统 → 连接学习通官方登录会话
  → 选择学习通课程、考试
  → 获取考生名单（姓名、学号、提交状态）
  → 读取答卷并创建本地阅卷记录
  → 大模型预评 → 教师确认或改分
  → 本系统保存评分、查看进度与导出成绩
```

这里的“大模型评估”指逐题评分、理由与必要建议。课程目标达成度、学生能力画像和完整错题体系不属于本阶段。

优先验证网页 + 服务端隔离浏览器；Chrome/Edge 扩展作为备选采集适配器。两条路线共享课程、考试、考生及答卷 DTO 和阅卷业务。服务端模式可在用户关闭网页后继续已授权的采集任务，前提是服务端会话仍有效；扩展模式未完成的采集依赖教师浏览器继续运行。两者已持久化的答卷都可独立进行后端评分。

### 2.1 实际读取路径

以下是源码使用的网页路径，不代表经过验证的官方稳定开放 API：

| 阶段 | 读取方式 |
|---|---|
| 登录 | `passport2.chaoxing.com/login`，进入官方页面完成登录 |
| 会话与课程首页 | `fycourse.fanya.chaoxing.com/fyportal/courselist/course`，结合 UID 类 Cookie 检测账号 |
| 指定学期课程 | `/fyportal/courselist/coursegroupdata`，携带 `sectionId`、`semesterNum` 等参数 |
| 激活课程上下文 | `/fyportal/courselist/entercoursenewfy`，从重定向结果解析 `courseid/clazzid/cpi/enc/t` |
| 考试列表 | `mooc2-ans.chaoxing.com/mooc2-ans/exam/test`，或经课程页 iframe 发现 |
| 考生列表 | 从考试链接进入 `exam/test/marklist`，解析 LayUI 表格及批阅链接 |
| 单份答卷 | 从考生链接进入 `exam/test/markpaper`，解析题干、答案、参考答案、分值与题型 |

动态考试页面不能只用后端 HTTP 请求替代：现有实现专门用浏览器正常导航等待 DOM，避免 HTTP 200 实际只返回空壳。扩展的导航等待为 20 秒，DOM 数据等待为 12 秒；移植时应统一整个请求预算，不能让页面消息桥先于内部等待超时。

源码当前允许五个学习通主机：`passport2.chaoxing.com`、`i.chaoxing.com`、`fycourse.fanya.chaoxing.com`、`mooc1-api.chaoxing.com`、`mooc2-ans.chaoxing.com`。原集成文档只列三个，已经落后于代码。

扩展自行发起的采集操作为 GET/导航，没有提交分数接口；官方网页加载时仍会运行自身脚本，不能将其表述为“浏览器中的全部网络请求都只有 GET”。

### 2.2 原实现的持久化与模型行为

- 名单保存姓名、学号、提交状态、来源总分和客观分等信息。
- 逐题保存题干、答案哈希、评分规则、预评分、教师确认分数、模型与版本信息；没有专门存储学生答案正文的列。模型生成的评分依据仍可能包含答案片段。
- 主观题单份答卷最多并发 3 题；界面根据耗时预评后续 1–5 位考生。这不是整场考试的持久化批处理任务。
- 当前模型策略是 DeepSeek 调用失败后尝试 Qwen，每个提供方选一条模型路由，并非双模型复核。
- 原实现既有完全相同答案复用，也有 SimHash 近似答案复用。
- 教师确认只保存在 ArkLoop，不回写学习通。

## 3. 本系统复用什么，以及需要补什么

| 能力 | 复用方式 |
|---|---|
| 教师登录与权限 | 使用当前本系统用户，所有学习通阅卷记录归属该教师 |
| 大模型配置 | 复用 `ProviderConfig / ModelConfig / RoleBinding` |
| 评分流程 | 复用主评、复核、可选仲裁、结构化输出校验与 Prompt |
| 评分证据 | 复用 `GradingTask / GradingResultSnapshot / GradingAuditEvent` |
| 人工评分 | 复用人工覆盖快照机制，新增外部答卷的确认和汇总逻辑 |
| 教师界面 | 阅卷中心增加学习通入口，复用评分展示、编辑和导出组件 |
| 外部考试记录 | 新增轻量考试、考生与逐题阅卷记录，不要求本地课程/学生/试题映射 |

主要实现入口：[阅卷模型](/Users/jzefan/work/proj/exam/backend/src/app/grading/models.py)、[阅卷服务](/Users/jzefan/work/proj/exam/backend/src/app/grading/service.py)、[现有后台调度](/Users/jzefan/work/proj/exam/backend/src/app/exams/student_router.py:905)。

现有阅卷服务并非完全独立于本地考试：权限、收件箱、结果回填和重启恢复大量依赖 `source_type == "exam_submission"`。因此，新的外部来源需要明确适配，不能仅改一个字符串后直接使用全部旧接口。

建议使用：

```text
source_type = external_exam
source_business_id = 本地外部逐题阅卷记录 UUID
```

逐题记录关联考生记录，考生记录关联外部考试，外部考试关联当前教师和学习通连接。来源类型通过这些关系找到所有者，无需学生 User 外键。

必要的适配有四处：

1. **任务权限**：扩展创建、读取、执行、报告、人工改分等共享访问检查，支持从外部阅卷记录解析教师归属。不能把普通教师请求改成管理员调用来绕过现有检查。
2. **结果落库**：新增 `apply_grading_result_to_external_exam` 一类业务服务，更新外部逐题记录与考生汇总；不调用原生学生答案回填服务。
3. **任务恢复**：后台调度按来源分派成功、失败和重试处理，并恢复未完成的外部任务。当前启动恢复只查询 `exam_submission`，必须扩展。
4. **页面与报表**：学习通名单、详情、进度和导出使用外部来源接口。现有本地考试报表直接查询 `ExamStudent`，不能原样复用其数据查询。

这样复用的是评分能力和界面组件，外部数据保持符合“教师阅卷工具”的业务范围。

## 4. 精简的数据设计

以下表名为拟议设计，尚未存在：

| 表 | 保存内容 | 关联与约束 |
|---|---|---|
| `external_connections` | 当前教师、提供方、学习通账号标识、连接模式、最近连接时间及会话引用 | 当前教师+提供方+外部账号唯一；不存密码或明文 Cookie，服务端模式的认证状态单独加密保管 |
| `external_exams` | 外部考试标识、课程/学期名称与标识、班级范围、考试名称、满分、来源状态、采集完整性 | 连接+规范化课程上下文+考试+范围唯一；课程信息直接保存为来源快照 |
| `external_exam_candidates` | 姓名、学号、源答卷关系标识、提交状态、学习通原分、客观分、AI 汇总分、确认分、进度 | 归属一场外部考试，不关联本系统学生账号 |
| `external_grading_items` | 考生记录、源题 ID、题序、题型、满分、题干/参考答案、必要作答内容、内容版本、任务 ID、AI 分、人工确认分及时间 | 考生记录+源题标识+内容版本唯一；当前版本指针避免旧任务覆盖新结果 |
| `external_sync_jobs` | 考试范围、预计/已读取/失败数量、断点、错误及状态 | 幂等请求键；可重试；不能以第一页读取成功标记全量完成 |

课程列表实时读取，选定考试时保存课程上下文，因此首版无需独立课程映射表。逐份答卷的完整性、内容摘要和版本可保存在考生记录中，逐题输入放阅卷项；模型输入以关联的 `GradingTask` 为实际快照，避免无意义地重复保存正文。

### 4.1 考生信息不等于学生身份体系

教师界面只需姓名和学号。后台另外保留学习通答卷链接中的 `testUserRelationId` 或等效源记录标识，用于定位答卷、去重和续传。这是技术键，不是新增学生账号，也不需要教师手工匹配身份。

```text
candidate_name：姓名，用于教师查看
student_no：学号，用于教师核对和成绩导出
external_record_id：本场考试内的源答卷/考生记录标识，用于去重
id：本地数据库记录主键
```

不按姓名自动合并考生，不按学号跨考试合并档案。两条同名或同学号但不同源记录应分别保留并提示核对。若某页只提供姓名、学号而没有稳定源标识，需要可靠获取批阅链接或使用考试范围内可核验的组合键；不能用表格行号在分页或重新排序后覆盖别人的成绩。

### 4.2 数据保留以阅卷为目的

必须保留：课程和考试信息、考生姓名/学号、来源成绩、逐题 AI 与教师确认分、总分、必要评语、模型/规则版本、确认时间及修改记录。

批改和复核期间需要保留必要评分输入：题干、参考答案、学生作答及内容哈希，以支持教师查看、异步评分和失败重试。这不等于建设完整学生错题档案；无需把题目导入公共题库、分析个人长期知识掌握或生成补练。

建议首版保留当前阅卷所需输入，不承诺完整保留所有历史原卷、附件和历次答案正文。批改结束后的正文清理可以作为独立保留策略，当前不擅自设定固定清理天数。

如果后续启用正文清理，必须同时处理 `GradingTask.student_answer_raw`、结构化答案、附件、外部记录及可能含答案片段的评分依据，不能只删一列就宣称答案已清除。结果、哈希和审计可继续保留；清理后再次看原答卷或重新评估，需要从学习通重新读取并核验内容版本。任务执行中、失败待重试和教师复核中的输入不得提前清理。

### 4.3 去重与重新评分

- 同一教师、学习通账号、考试、答卷、题目及输入版本重复读取，只恢复已有进度。
- 输入哈希覆盖答案、题干、参考答案、分值、评分规则、Prompt 与模型配置版本；不能仅以答案文本判断是否可复用。
- 答案或标准答案变化时创建新阅卷版本，当前题目重新进入待评分/待确认，保留此前分数与确认记录；不强制永久保存全部历史正文。
- 教师确认附带输入版本和评分版本；后台任务晚返回不能覆盖较新的答案、模型结果或人工确认。
- 不将重复同步显示为学生再次参加考试。
- 源提交时间未知时保持为空，单独记录采集时间；本方案不再受本地 `StudentExamSubmission.submitted_at` 非空约束影响。

## 5. 六个业务步骤怎样落地

### 5.1 连接学习通

在阅卷中心增加“学习通”入口。优先路径：创建服务端隔离浏览器会话 → 弹出网页登录窗口展示远程浏览器中的学习通官方登录页 → 教师完成登录/额外验证 → 后端确认账号与读取权限。这里需要远程浏览器画面及输入转发，不能用普通跨域 iframe 假装已经解决会话读取。

服务端保管真实认证状态，前端只持有绑定当前教师的连接 ID，不返回学习通 Cookie/token。备选扩展路径才是检测扩展版本 → 打开本机官方登录页 → 扩展探测本机账号，Cookie 留在教师浏览器。

若启用扩展备选，同步修改 `manifest`、`content.js` 和 `background.js` 的来源限制：ArkLoop 当前认可本地 5173/19080 及 ArkLoop 域名，本系统 Vite 默认端口为 4000。正式域名在发布时明确配置。

任一连接模式切换学习通账号时挂起旧采集、清空会话级缓存并重新确认连接上下文，避免将新账号读取的数据写入旧账号考试。已有本地评分仍可查看。

### 5.2 获取课程列表

复用学期、课程读取与入口跳转，教师直接选择课程，不增加绑定本地课程或创建班级的步骤。

课程跳转可能补齐 `clazz_id`。ArkLoop 内部 `resolveChaoxingCourse()` 修正复合键后，公开的 `listChaoxingExams()` 只返回考试数组，界面的 `selectedCourse` 可能仍使用旧键；移植时应显式更新规范化课程上下文。

原实现考试入口可能使用 `clazzid=-1` 表示全部班级，应保留实际采集范围。班级可作为来源信息展示，不要求建立本地班级档案。

### 5.3 获取课程考试

复用考试列表、分页与 iframe 发现，选中后建立外部考试记录。展示考试名称、提交人数、满分与本地阅卷进度。

零提交考试可以查看元数据，但没有可评答卷。学习通考试状态与本地阅卷状态分开保存。

外部考试不会创建原生 `Exam`，所以无需接入学生开考、交卷、补交或重考接口，也无需为此修改原生考试状态机。

### 5.4 获取考生信息与答卷

分页读取名单，以姓名、学号、提交状态为主展示。逐份获取已提交答卷，保存本次批改所需输入。

单份答卷事务：验证来源键、题目和分值 → 保存考生及阅卷项 → 创建评分任务 → 提交事务。网页读取与模型调用放在事务之外。可先评估已完整采集的答卷，整场进度继续显示待采集与失败部分。

未提交、读取失败、部分读取与评分完成是不同状态，不能统统计为 0 分。不同学生题目不同或顺序不同，按各自答卷的源题 ID、题序与满分记录，不要求统一生成本地试卷。

### 5.5 大模型评估

增加外部答卷 DTO → `GradingTask` 的适配器，复用本系统评分引擎。模型只接收题干、参考答案、规则与作答，不需要姓名和学号。

本系统种子配置为 Qwen 主评、DeepSeek 复核、Doubao 仲裁角色，实际以数据库绑定及仲裁开关为准；这与 ArkLoop 的 DeepSeek 失败后回退 Qwen 不同。推荐先沿用本系统策略，后续再按成本和效果提供可选配置。

| 数据类型 | 首版处理 |
|---|---|
| 简答、论述 | 使用本系统主观题评分能力 |
| 编程题 | `programming` 映射 `code`，保留换行缩进；无运行测试时明确为静态评估 |
| 选择、判断、已有可靠源得分的填空 | 保留学习通得分，通常无需重复调用模型 |
| 需要语义评分的填空 | 明确每空答案与分值后适配填空能力，汇总遵循记录的评分类别 |
| 必要图片/附件无法读取 | 标记待人工，教师核对原答卷后在本系统评分 |
| 标准答案不足 | 提示教师补充评分依据或人工复核 |

### 5.6 评分结果保存与导出

模型结果保存到评分任务快照，并更新外部阅卷项。教师可接受 AI 分或修改后确认；AI 失败时也允许教师直接评分。

名单展示：姓名、学号、学习通客观分、AI 主观分、教师确认主观分、当前总分、阅卷进度。学习通原总分单独保留作参考，不与重新评估后的总分相加。

正式总分 = 已核实的客观分 + 本次所有需教师确认题目的确认分。客观分缺失或仍有未确认/失败题时，只展示暂计分与进度；不能把缺失当作 0。既有客观题明细与来源客观总分只能选一种汇总依据，避免重复计入。

导出至少包括课程、考试、姓名、学号、客观分、AI 主观分、确认主观分、总分与确认状态。可导出未完成记录，但应明确标记，不能混入正式成绩统计。

结果仅供教师在本系统查看和导出；不发送学生通知，不进入学生错题本，不实现向学习通提交或回填分数的操作。

## 6. 仍需处理的技术边界

| 问题 | 证据与处理 |
|---|---|
| 分页不完整 | ArkLoop 会跳过部分读取失败，考试/名单有 10/50 页上限；返回预期、已读、失败、截断及完整性状态，避免静默漏人 |
| 多页答卷未合并 | `getChaoxingReview()` 选主观题最多的一页；应按源题 ID 合并并检查冲突 |
| 代码格式丢失 | `cleanText()` 折叠所有空白；代码单独提取，保留缩进和大小写 |
| 混合图文漏判 | 原 `manual_review` 仅在有附件而无文本时置 true；必要附件未读到也应人工处理 |
| 小数分值 | 本系统 `GradingTask.max_score` 和 Schema 为整数；接入时支持小数，避免先 round 再评分 |
| 模型失败无法直接重试 | ArkLoop 同哈希且非 pending 就返回，包含 failed；新增显式重试逻辑 |
| 不可靠分数复用 | 首版可先不启用跨考生答案复用；以后启用时仅在完整评分输入一致时复用，不依据 SimHash 近似度直接搬运分数 |
| 任务来源适配 | 权限、恢复、结果写入、人工确认和列表查询支持 external_exam，不能假装 exam_submission |
| 整卷确认口径 | 每题记录确认状态，全部必要评分项确认才标整卷完成；失败不等于完成 |
| 持久化调度 | 共享并发限制；首版单调度者可恢复，多实例需任务领取租约防重复执行 |
| 账号切换 | 教师+学习通账号+考试隔离；同步批次绑定账号，拒绝错误上下文数据 |
| 外部网页兼容 | 真实页面可能变化，需要实际教师账号验证；现有模拟测试不能代替现场联调 |

原方案中“本地学生匹配、课程班级映射、原生交卷、学生错题恢复、原生考试成绩回填”等工作已经移出本阶段。新的必需工作是外部来源适配与教师阅卷记录。

## 10. 网页免安装连接的实施决策

### 10.1 普通弹窗的边界

普通网页可以打开学习通官方登录页，但不能因此读取跨域窗口内容或认证凭据。`postMessage` 也需要对方页面主动合作，不能替代不存在的授权回调。[MDN：window.open 与同源限制](https://developer.mozilla.org/en-US/docs/Web/API/Window/open)。

免安装并不等于所有工作都在用户浏览器完成。可验证的路线是服务端运行浏览器，由教师通过网页远程完成官方登录，然后同一服务端浏览器继续读取考试信息。

```text
教师网页弹窗（远程交互画面）
  ↔ 当前教师专属登录会话
  ↔ 服务端浏览器中的学习通官方登录页面
  → 验证账号与课程读取能力
  → 同一浏览器会话读取考试、名单、答卷
  → 外部阅卷数据 → 本系统评分引擎
```

这是本项目拟议架构，不是已经验证学习通支持的官方连接方式。ArkLoop 的 DOM 解析和导航经验可复用，但其本机扩展/桌面登录桥不能直接变为服务端网页登录桥。

### 10.2 登录与会话保管

- 不把登录状态假设为一个固定 token；可能涉及多个 Cookie、浏览器存储与页面临时参数。优先在原浏览器上下文继续读取，只有经过验证才将部分请求优化为 HTTP 调用。
- 使用 Playwright 一类工具管理独立 BrowserContext；它提供 Cookie/存储隔离，但不能代替产品的教师权限检查、远程会话鉴权和服务端隔离措施。[Playwright 隔离说明](https://playwright.dev/docs/browser-contexts)。
- 首个验证版本让用户操作远程官方登录页，遇到验证码、短信验证等由用户完成。不要先逆向全部账号密码登录协议，也不实现自动绕过验证。
- 若以后增加自建用户名/密码表单，要明确密码会经过本系统后端，作为一次性输入处理，不写库、不记录请求体，也不让登录抓包、追踪和截图泄漏凭据。远程官方页面方案同样经由托管浏览器和输入通道，不能宣传为“服务器完全接触不到密码”。
- 服务端认证状态应单独加密保存或只在会话存活期间保留，设置断开清除和失效重登；前端只拿本系统连接 ID。Playwright 官方说明认证状态可包含足以冒用账号的 Cookie/headers，因此不能进入仓库、日志或普通附件。[Playwright 认证说明](https://playwright.dev/docs/auth)。
- 登录成功需通过实际课程读取验证，不仅判断页面跳转或某个 Cookie 存在。具体登录方式和会话恢复能力以真实账号实测为准。

### 10.3 非官方接入的实际问题

1. 页面结构和内部请求参数没有本项目掌握的稳定契约；调整后可能需要更新解析器。
2. 目标服务器出口、浏览器环境、会话时效和额外验证是否影响登录，需要实测，不能由本机扩展测试推断。
3. 数据可能分页或异步加载；必须验证人数、题数和分值，避免读取失败后生成错误成绩。
4. 服务端托管浏览器增加运行资源和并发排队成本，网页免安装只是降低教师端门槛。
5. 教师授权和不回写不等于平台承诺支持这种访问方式；推广前仍需核实实际适用的平台规则及学校要求。本轮未核查具体协议，不作已获允许或禁止的判断。

不承诺永不失效。产品应能提示重新登录、恢复断点，并保留已完成的本地评分。登录验证可能需要 POST，业务上的只读指不提交答卷、不修改学习通分数，不应以“所有请求必须 GET”破坏正常登录。

### 10.4 先验证再建设

第一项实现任务仅验证：在拟部署服务器完成一次教师交互登录 → 读取课程 → 读取一场考试及完整名单 → 读取一份典型答卷 → 保持/恢复会话后再次读取。

测试还应确认断开连接清理、账号切换隔离与过期重登。若该路径持续被额外验证或环境限制阻断，保留相同数据契约，切换扩展备选；不无限投入绕过限制，也不先完成整套远程浏览器产品再验证学习通。

## 11. 本次开发的模型与成本策略

以下为开发本功能时的编程模型建议，不代表上线阅卷模型配置变化，也不表示已经切换当前任务模型。

| 模型 | 本项目建议职责 | 建议起始推理档位 |
|---|---|---|
| GPT-5.6 Sol | 主力开发；服务端登录验证、会话生命周期、后端任务与跨模块接入 | medium，遇到复杂问题再提高 |
| GPT-5.6 Terra | 规格明确后实现列表、状态展示、DTO、导出及基于样本的解析测试 | medium |
| GPT-6 Astra | 会话架构关键检查、顽固跨层问题、里程碑重点审查 | 按问题使用，避免常驻执行全部任务 |

这是根据本项目不确定性做的分工建议，不是三种模型在本仓库的实测质量排名。先比较一个明确任务的测试通过情况、修复次数和消耗，再调整职责；小模型反复失败时应携带精简复现交给 Sol/Astra，不让其无限重试。

截至本次核对，官方信用点标准费率（每百万 token）如下；这不是每次任务固定收费，也不代表用户具体套餐账单：

| 模型 | 输入 | 缓存输入 | 输出 |
|---|---:|---:|---:|
| Astra | 250 | 25 | 1250 |
| Sol | 100 | 10 | 500 |
| Terra | 50 | 5 | 300 |

相同 token 数和类别下，Sol 是 Astra 标准费率的 40%；Terra 输入为 20%、输出为 24%。真实任务节省取决于缓存、上下文、推理量和返工。官方当前说明 Astra Fast 模式为标准费率的 2.5 倍；没有速度硬要求时优先标准模式，用户当前是否启用 Fast 尚未核实。[官方产品定价](https://learn.chatgpt.com/docs/pricing)。

若使用 API key 计费，应采用 API 费率而非信用点表：当前标准短上下文输入/输出分别为 Astra $10/$50、Sol $4/$20、Terra $2/$12，单位为每百万 token；缓存、长上下文和速度档位另计。[官方 API 定价](https://developers.openai.com/api/docs/pricing)。

具体控制方式：

- 按“连接验证、采集解析、阅卷落库、前端与导出”拆成有验收标准的任务，日常由 Sol 推进。
- 每次给出所需文件、数据契约与测试命令，不让模型反复重新分析整个 ArkLoop 和 exam 仓库。
- 保留简短交接说明和测试结果；使用已有方案作为上下文，不复制冗长工具日志与真实答卷。
- UI/字段等边界清楚的工作交 Terra，关键节点再做一次集中审查，不为每个小改动调用 Astra。
- 页面读取及 DOM 解析使用确定性程序；产品不需要为每次打开学习通页面额外调用编程模型。
- 未经用户请求不自动创建多模型并行任务；分工可通过逐个任务选择模型完成，减少重复读取上下文。

以上模型分工尚未自动应用，也未切换当前任务模型。后续实现已新增服务端登录窗口和只读采集原型，连接与解析过程不调用大模型。
