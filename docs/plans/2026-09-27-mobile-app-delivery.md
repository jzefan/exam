# 移动端 PWA 安装与更新方案

**当前决定（2026-09-27）：**先通过浏览器“添加到主屏幕”分发；原生 App 与应用商店暂缓，之后再评估。

## 目标与现状

教师在 iPhone 和 Android 上进入工作台、课程、阅卷中心、学生管理。用户首次从浏览器添加到主屏幕后，普通网页界面与文案随服务器部署更新，不要求重新安装。

现有前端是 React/Vite 单页应用，已提供 `standalone` Web App Manifest、主屏幕图标、Service Worker 和版本检查。`nginx.conf` 对入口 HTML 与 Service Worker 禁止长期缓存，对带内容哈希的静态资源长期缓存。API 以同源 `/api` 调用。当前最短可用路径是完善并发布 PWA；用户从 Safari/Chrome 添加到主屏幕后即可像 App 一样打开，网页部署后由现有更新机制获取新版本。

## 分发决策

| 路径 | 安装与更新 | 适用条件 | 主要限制 |
| --- | --- | --- | --- |
| PWA（已选择） | 浏览器添加到主屏幕；服务器发布更新网页内容 | 当前交付方式 | 安装入口和部分系统集成受浏览器/系统限制 |
| iOS/Android 原生容器（暂缓） | 商店安装原生程序；网页内容由服务器按受控策略更新 | 以后确有商店或系统集成需求时再评估 | 原生功能、权限、插件和商店元数据变更需重新发版；iOS 有最低功能与动态代码审核要求 |

不要将 Capacitor 的 `server.url` 当作生产版远程网站容器配置：其官方文档明确标记为实时重载开发用途。若选择 Capacitor 打包本地网页资源，现有相对 `/api` 请求需要改成按环境配置的 HTTPS API 地址；网页增量更新还需要版本清单、签名/完整性校验、灰度、回滚与关键操作延迟切换。若选择直接由原生 WebView 加载受控 HTTPS 站点，则要实现域名白名单、外链与下载处理、离线/连接错误页、登录状态、系统返回键、文件选择、键盘和安全区适配，并评估 App Store 4.2 最低功能审核风险。不能把“套一个网站”视为必然通过审核。

## 功能边界

- 工作台、课程列表与详情、阅卷队列、学生列表共享现有 React 路由和 API，不复制一套移动端业务逻辑。
- 手机上优先保证查看和处理高频任务；复杂配置仍可通过响应式页面完成，原生容器只提供必要的系统能力。
- 账号、权限、数据校验继续由服务端统一处理。WebView 内的登录会话与 Safari/Chrome 独立，需按产品要求选择重新登录或安全地对接统一登录。
- 更新时不得打断学生考试和教师阅卷；已选阅卷任务所在路由先延迟自动刷新。其他有未保存输入的流程应在接入原生容器前逐一盘点。
- 每次部署保留可回退的静态版本。若新版加载失败，给用户可见的重试/恢复入口；不在关键流程强制换版。

## 实施顺序与验收

1. **PWA 首版**：完成响应式四个教师入口；在用户菜单提供安装指引；延迟关键操作期间的自动刷新。
2. **服务器发布后真机验收**：iPhone Safari 与 Android Chrome 分别安装到主屏幕，检查独立窗口、登录、四个入口、阅卷保存、离开阅卷后的版本更新和返回浏览器后重新打开。当前代码验证不能替代这一步。
3. **后续再评估原生容器**：确有商店或系统能力需求时，再确定平台、生产域名、应用名称、Bundle ID/Package ID 与架构，不提前创建原生工程。
4. **发布与回滚**：保留可回退的网页构建版本；验证已安装 PWA 能获取部署后的新版本。PWA 的联网业务操作仍要求服务器可用。
