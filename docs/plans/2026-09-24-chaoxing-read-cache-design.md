# 学习通读取缓存设计

日期：2026-09-24；实现更新：2026-09-25。范围：教师课程、考试与作业、考生名单、考生答卷的读取与重复访问，以及点击 AI 评分时的保存与去重。

## 现状与慢点

- `browser.Session` 已有 5 分钟、最多 32 项的进程内读取缓存。课程、考试与作业、名单、答卷四级接口都会使用它；刷新绕过缓存。缓存随连接断开、空闲 30 分钟、连接最长 2 小时或服务重启消失。
- 每位教师的浏览器操作由同一会话锁串行执行。一次考试列表读取可能访问课程页、考试页、作业页和任务模块；名单与答卷还可能访问多页，并等待动态表格。批量评分逐份串行读取答卷。缓存命中能省去这些源站请求，但 32 项容量在一场考试中很容易耗尽。
- 前端设置 `cache: "no-store"`，API 也返回 `Cache-Control: no-store`。这是正确的浏览器缓存边界；共享缓存应由后端按教师和学习通账号管理。
- 现有 `chaoxing_grading_*` 表只保存主动导入的阅卷数据。它们有版本、确认和评分语义，不能直接当作“所有浏览过内容”的缓存。
- 当前单人和整场 AI 评分均先调用答卷导入接口，再提交评分任务；同一答卷哈希不会重复创建版本，同一版本已入队的题目不会重复入队。但整场流程仍逐人读取源站答卷、导入后才发现 `queued: 0`，因此已评分考生也会产生不必要的源站读取。
- 已实现分类型会话缓存和 PostgreSQL 快照；快照键按教师、学习通账号及父级业务 ID 隔离。缓存 API 响应带 `source`、`fetched_at`、`stale`，前端显示缓存来源时间。过期快照仍可浏览，教师可用刷新入口取源站最新数据。
- 已实现整场评分预查：最新保存版本已评分或正在评分的考生会在答卷读取前跳过；已保存但待评分的答卷直接入队；未保存的答卷先实时读取、保存再评分。单人重复点击对已保存答卷直接使用现有记录，不重复导入或生成版本。
- 当前列表 `complete: false`，表示分页完整性尚未证明。缓存不得把“读取过”改写成“已完整同步”。

## 推荐方案

采用“会话热缓存 + PostgreSQL 规范化快照”，暂不引入 Redis。现有部署已有 PostgreSQL，学习通连接器也被限定为单 API 进程；单独加 Redis 不会解决源站链接恢复、账号隔离、答卷新鲜度和导入校验，反而增加部署与敏感数据管理。以后如果多实例或跨主机扩容，再评估 Redis 作为短期热缓存。

### 第一层：改进现有会话缓存

保留当前 `Session.records` 中的读取链接和签名参数，只在进程内使用。将统一的 5 分钟/32 项策略改成按类型配置的 TTL、容量与总字节上限，并加入命中率、源站读取耗时、页数、超时数指标。建议初值如下，实际用运行数据调整：

| 类型 | 新鲜期初值 | 会话容量初值 | 说明 |
| --- | --- | --- | --- |
| 学期、课程 | 30 分钟 | 各学期合计 20 项 | 变更少；仍保留手动刷新 |
| 考试、作业 | 5 分钟 | 50 项 | 已提交人数会变 |
| 考生名单 | 2 分钟 | 50 项 | 正在考试时新增提交较频繁 |
| 答卷 | 30 分钟 | 200 份，另设总字节上限 | 避免整班读取后早期答卷被逐出 |

每次成功读取才更新缓存；解析失败、登录过期、部分读取异常不得覆盖上次成功结果。缓存命中保持目前的返回速度和 `no-store` HTTP 头。刷新具体考试或名单时失效其下级缓存；避免通过一个宽泛前缀删除其他考试的答卷。多个请求读取同一键时复用一次源站任务，避免并发重复抓取；当前单会话锁已提供部分串行保护。

### 第二层：一张 PostgreSQL 读取快照表

在需要“重新登录或部署后仍能秒开上次读取内容”时增加一张独立表，例如 `chaoxing_read_snapshots`。每个列表或答卷保留最新成功快照，而非“每访问一次插入一行”。源站成功返回时更新读取时间；内容哈希变化时才替换 `payload`，访问缓存不写库。

建议按“学期课程列表、某课程考试/作业列表、某考试名单、某考生答卷”存四类快照，而不是每一行单独存一份。字段包括 `owner_id`、`account_key`、`kind`、`parent_source_key`、`source_key`、`payload JSONB`、`content_hash`、`fetched_at`、`fresh_until`、`purge_after`、`schema_version`；唯一键为 `(owner_id, account_key, kind, parent_source_key, source_key)`。`fresh_until` 决定是否需要刷新，`purge_after` 决定何时清理。查询从已验证的教师身份和学习通账号出发，不能只按前端传入的对象 ID 查询。`payload` 只存解析后的展示字段及已有媒体 ID；不存 Cookie、密码、原始 HTML、完整源站 URL 或 `enc` 等签名参数。答卷的题目与答案需要单独的保留期和容量上限；建议先按 7 天清理未导入快照，再依据实际使用调整。已主动导入的阅卷记录遵循原有版本与保留规则，不受临时快照清理影响。

原有 `source_id` 可作为业务键，但课程键还需学期上下文，考试键还需课程上下文，考生键还需考试上下文；缓存层用显式的父级源键组成完整路径。前端仍使用当前会话记录 ID，后端从已授权快照重建这些 ID 与父子关系；记录 ID 不承担授权功能，所有权始终在服务端核验。

## 读取、刷新与保存语义

1. 登录验证仍必须确认当前学习通账号和有效授权。当前 `verify` 会读取课程页，且在课程读取结束后才设置 `account_key`；接入持久快照时需要调整这一步的顺序，并继续验证源站登录有效。可另行优化为轻量验证，但不能仅凭本地快照认定源站仍已登录。取得 `account_key` 后，后续四级列表可优先返回该教师和账号的快照。
2. 快照有“本次读取时间”和“是否超过新鲜期”两个状态。新鲜快照直接返回；过期快照可以先展示，并明确显示“上次读取于 …”，随后在有当前源站链接时异步刷新。源站不可用时保留旧快照并显示错误，不把旧数据伪装成实时数据。
3. 跨会话快照不含源站链接，所以可直接用于浏览，但点击“重新读取”、首次读取缺失内容或需要保存/批量评分时，应沿课程 → 考试 → 名单逐级恢复当前会话内的链接，再读取相应答卷。恢复失败只影响实时操作，已有快照仍可查看。
4. 同一连接内刚从源站取得的答卷仍按现有 `review_hash` 导入。仅从临时读取快照恢复、尚未正式导入的答卷先作为预览；首次保存或评分前必须实时重读该份答卷并核对哈希及完整性，防止把过时或不完整的答卷当作当前版本导入。已经正式导入的答卷属于持久阅卷记录，可以直接继续评分，无须为“补评未完成题目”再次读取源站。若产品将来允许“按未导入的历史快照评分”，须另设明确操作和来源时间标记。
5. 手动刷新绕过两层缓存；成功后原子替换快照，并按父子关系失效下级。刷新失败保留旧快照。只有源站明确返回的空列表可以短期缓存；未识别页面和超时不作为空列表缓存。名单与考试的提交人数仍逐项核对，`complete: false` 原样保留。
6. 切换学习通账号时按 `account_key` 隔离。断开连接立即清掉会话热缓存和链接，但保留该教师自己的数据库快照。清除账号凭据与清除读取快照应提供独立操作；账号授权或教师权限变化后，后端查询仍须重新核验所有权。

## 接口与界面最小改动

- 四级读取接口维持现有路径和 `refresh=true`，响应增加 `source: "live" | "session" | "snapshot"`、`fetched_at`、`stale`；前端在列表和答卷处以小字显示“上次读取时间”，过期时给出“重新读取”。
- `readable` 应区分“有快照可查看”与“当前会话有可用源站链接”；否则重连后缓存项看似可刷新，实际 `_url` 缺失。可以增加 `can_refresh`，并让后端负责逐级恢复链接。
- 答卷预览有一个明确的 `can_import` 状态。临时快照恢复时先禁用首次保存/评分；实时核对成功后解除。已正式保存的答卷可直接继续未完成的评分。批量评分若从缓存名单启动，先核对当前提交人数与名单，再只对尚未正式保存的考生逐份实时读取答卷。
- 浏览器和反向代理继续使用 `no-store`，不能通过 HTTP 共享缓存承载学生答卷。

## 点击 AI 评分时的持久化与跳过规则

**单人和整场使用同一规则：先持久保存试卷内容、考生作答及媒体，再创建 AI 评分任务。** 保存至少包含考试来源、课程与考试名称、该考生本次试卷的题目/顺序/题型/参考答案/分值、考生每题作答与源分、媒体引用和内容哈希。当前 `ExternalExam` + 按考生版本保存的 `ExternalCandidate`/`ExternalItem` 已具备大部分字段；需核对富媒体是否完整纳入保存版本。不同考生可能抽题或题序不同，不能仅用一份“全场共享试卷”替代每位考生的实际试卷。AI 任务入队前必须提交持久数据；评分失败或中断也保留答卷，供教师查看与重试。只有成功读到并正式导入的考生答卷才进入这些长期记录，普通浏览仍走有保留期的读取快照。

整场 AI 评分先根据当前教师、已验证的学习通账号、课程源 ID、考试/作业源 ID、考生源 ID，**批量查询已保存状态，再开始逐人处理**，避免对已评分考生发起答卷读取请求。判定只针对该考生最新的已保存答卷版本：

| 已保存状态 | 整场点击后的处理 |
| --- | --- |
| 未保存 | 从源站读取该份答卷 → 持久保存 → 为可自动评分题目入队 |
| 已保存，尚有未入队题目 | 直接基于已保存版本入队；不重复读取或保存 |
| 已入队或正在评分 | 跳过，避免重复任务与模型费用 |
| 可自动评分题目都已取得 AI 结果或已由教师确认 | 跳过该考生，直接处理下一个 |
| 部分题目失败 | 只重试失败题目；已有 AI 结果和确认分不重算 |
| 没有可自动评分题目 | 保留已保存答卷，单独计入“无需 AI 评分”，不算“已评分” |

单人再次点击 AI 评分也使用相同幂等判定；已经完成时直接打开已保存阅卷详情并提示“已评分”，不把 `queued: 0` 当成启动失败。名单状态查询和任务创建均在服务端进行所有权校验；对同一考生的并发点击使用数据库行锁与唯一约束保证只创建一次任务。整场流程展示“新提交评分 / 已评分跳过 / 评分中跳过 / 失败重试 / 无需 AI / 读取失败”各自数量。

“跳过已评分”以**最新已保存版本**为准，因此能直接省掉源站请求，也意味着整场重复点击不会主动探测学习通是否改卷。教师主动“重新读取答卷”发现内容哈希变化时生成新版本；旧版评分保留为历史，新版重新进入待评分状态。若以后需要每次整场运行都自动检查源站更新，应提供单独的“先同步全部答卷”操作，因为那会重新产生逐人读取耗时。

## 实施顺序与验收

1. 已完成分类型会话 TTL/容量、URL-free PostgreSQL 快照、过期清理、跨会话快照浏览和刷新恢复，以及 AI 评分预查与去重。
2. 后续可增加真实使用指标并评估是否需要后台自动刷新；当前过期快照会带时间提示，由教师手动刷新。

验收用例：同连接重复访问和 100 份答卷回访命中；重启后同账号秒开快照；教师或学习通账号切换不串数据；刷新某考试不影响另一考试；新增提交后名单能更新；源站失效仍能看旧快照但不能把旧答卷当新卷导入；失败读取不覆盖成功快照；数据库快照与已导入阅卷记录互不影响。首次单人和整场 AI 评分均能在任务创建前查到完整保存的试卷与作答；第二次整场评分对已完成考生不产生源站答卷请求或新模型任务；已保存未评分者直接入队；失败者仅重试失败题目；主动刷新出新答卷版本后可重新评分。记录每级 P50/P95 响应时间、缓存命中率、源站页数、AI 任务去重数及快照表体积，达不到改善目标再考虑更深的源站读取优化。
