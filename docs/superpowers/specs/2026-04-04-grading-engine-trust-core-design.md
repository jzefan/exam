# 评分编排与可信度内核设计

- 日期：2026-04-04
- 主题：阅卷中心一期子项目一
- 范围：评分引擎优先，聚焦评分编排与可信度内核

## 1. 背景与目标

阅卷中心的整体需求同时覆盖题目与答案输入、多模型协同评分、人工干预、界面工作台、批量阅卷和单题调试。基于本轮需求澄清，一期不适合作为单一“大而全”项目直接设计和实现，需要按目标拆分。

本次设计聚焦的子项目是“评分编排与可信度内核”。该子项目的目标不是解决所有数据入口和所有前台操作，而是先回答最关键的问题：系统给出的分数是否可信、可解释、可复核、可追溯。

一期核心目标如下：

1. 为代码题和简答题提供统一的评分任务编排内核。
2. 支持多模型角色协同评分、程序化分歧检测和仲裁。
3. 支持结构化评分量表，而不是仅依赖自然语言 Prompt。
4. 对代码题接入沙箱运行与单元测试结果，提升功能正确性判断的可信度。
5. 支持人工重评、人工改分和评语补充，并保留完整审计链路。
6. 为后续 OCR、文件导入、考试系统导入、批量阅卷和调优工作台提供稳定底座。

## 2. 非目标

本设计明确不覆盖以下内容的完整实现细节：

1. OCR 识别引擎本身的算法设计。
2. 文件导入、考试系统对接的全流程接入实现。
3. 阅卷中心前端工作台的完整交互与视觉设计。
4. 开放性问题评分策略的完整细化。
5. 所有供应商模型的统一治理平台。

这些能力会在后续子项目中围绕当前内核继续扩展，但不会反向侵入本期核心评分链路。

## 3. 项目拆分与推荐顺序

阅卷中心建议拆分为三个子项目：

1. 评分编排与可信度内核。
2. 采集与导入层。
3. 阅卷工作台与调优台。

推荐优先顺序也是上述顺序。原因是当前一期最重要的成功标准是“评分可信”，因此需要优先构建统一任务模型、结构化量表、多模型仲裁和审计体系。只有当底层可信内核稳定后，采集入口和工作台能力才有稳定基础。

## 4. 一期范围与边界

本期内核采用“混合题型一期”的范围定义：

1. 支持代码题评分。
2. 支持简答题评分。
3. 为开放题预留扩展接口，但不在本期展开评分细节。
4. 同时服务单题调试和批量任务两种模式，但两者共用同一个评分内核。
5. 支持全入口接入，但只要求上游将内容转换为统一评分任务，不要求导入逻辑和评分逻辑耦合。

系统边界如下：

- 上游负责把题目、学生答案、标准答案、评分规则、来源信息转成统一评分任务。
- 内核负责对评分任务进行准备、评分、复核、仲裁、合成、审计。
- 下游消费统一的评分报告、审计记录和任务状态。

## 5. 设计方案选择

围绕“评分编排与可信度内核”，曾比较以下三种设计路线：

### 5.1 强编排工作流

将评分过程拆为固定节点：

1. 预处理。
2. 量表装配。
3. 主评分模型。
4. 审核模型。
5. 分歧检测。
6. 仲裁。
7. 结果归档。

优点是链路清晰、易审计、易复现、适合异步批量任务，也便于后续加入规则节点。缺点是灵活性略弱，新增题型时需要显式扩展节点逻辑。

### 5.2 Agent 式自由协同

由中心调度器驱动多模型动态协作完成评分。优点是灵活，适合复杂开放题。缺点是评分决策路径难以审计，复现成本高，不利于一期建立可信度。

### 5.3 规则优先加模型补充

通过规则引擎主导打分，模型主要负责语义理解和评语生成。优点是稳定可控，缺点是对简答题和表达差异容错较差，容易退化为硬匹配。

### 5.4 最终选择

本期采用“强编排工作流”方案，并在各节点内部保留题型和模型的扩展接口。该方案最符合“评分可信、可解释、可追溯”的目标。

## 6. 核心业务链路

评分编排与可信度内核的核心链路如下：

1. 创建评分任务。
2. 根据题型和配置装配评分上下文。
3. 评分老师独立评分。
4. 评分审核独立复核。
5. 程序化检测分歧与高风险标记。
6. 视规则触发最终评判仲裁。
7. 合成最终评分结果。
8. 写入结果快照和审计事件。
9. 在必要时接受人工重评或改分。

关键原则如下：

1. 所有入口统一进评分任务。
2. 所有模型统一吃结构化量表。
3. 所有结果统一出评分快照和最终报告。
4. 所有人工操作都以追加记录方式存在，不直接覆盖原始 AI 结果。

## 7. 核心数据模型

### 7.1 评分任务 GradingTask

评分任务是系统中的最小编排单元。设计上不直接以“考试”或“整份试卷”作为评分最小单位，而是以“某道题的一次评分过程”作为最小业务单元。

GradingTask 至少应包含以下字段分类：

#### 任务标识

1. `id`
2. `source_type`，例如单题调试、批量任务、OCR、文件导入、考试系统导入
3. `source_business_id`
4. `created_by`
5. `created_at`
6. `status`

#### 题目上下文

1. `question_id`
2. `question_type`
3. `question_content`
4. `subject`
5. `language`
6. `max_score`
7. `knowledge_tags`
8. `fatal_rule_enabled`

#### 作答内容

1. `student_answer_raw`
2. `student_answer_structured`
3. `ocr_raw_text`
4. `ocr_repaired_text`
5. `attachment_refs`

#### 评分依据

1. `standard_answers`
2. `rubric_definition`
3. `scoring_points`
4. `dimension_weights`
5. `deduction_rules`
6. `fatal_error_rules`
7. `prompt_template_version`
8. `role_binding_version`

#### 执行补充

适用于代码题：

1. `programming_language`
2. `execution_env`
3. `test_summary`
4. `compile_result`
5. `runtime_result`
6. `runtime_logs`
7. `resource_limit_summary`

#### 当前结果索引

1. `latest_primary_snapshot_id`
2. `latest_review_snapshot_id`
3. `latest_arbitration_snapshot_id`
4. `latest_final_snapshot_id`
5. `latest_manual_snapshot_id`

### 7.2 结果快照 GradingResultSnapshot

每次评分阶段都生成不可变结果快照，包括但不限于：

1. 主评分结果。
2. 审核评分结果。
3. 仲裁结果。
4. 人工改分结果。
5. 人工补评语结果。

每个快照应至少记录：

1. `id`
2. `task_id`
3. `snapshot_type`
4. `score_total`
5. `dimension_scores`
6. `deduction_reasons`
7. `strengths`
8. `improvement_suggestions`
9. `evidence_summary`
10. `risk_flags`
11. `provider_config_id`
12. `model_config_id`
13. `prompt_template_version`
14. `role_binding_version`
15. `created_by`
16. `created_at`

### 7.3 审计事件 GradingAuditEvent

审计事件用于记录评分链路中所有关键动作，至少包含：

1. `id`
2. `task_id`
3. `event_type`
4. `event_payload`
5. `operator_type`
6. `operator_id`
7. `created_at`

## 8. 多模型角色与接入架构

### 8.1 角色层与接入层分离

系统将“模型角色”和“模型接入”分离：

1. 角色层负责定义谁担任评分老师、评分审核、最终评判。
2. 接入层负责处理 provider、鉴权、base URL、超时、重试、限流和响应适配。

当前已知接入约束如下：

1. Qwen 使用独立 API Key。
2. DeepSeek 使用独立 API Key。
3. Claude 通过 OpenRouter Key 接入。

因此系统至少需要支持以下 Provider 配置：

1. `qwen-direct`
2. `deepseek-direct`
3. `openrouter`

### 8.2 配置抽象

建议引入以下三个配置对象：

#### ProviderConfig

记录 provider 类型、鉴权引用、base URL、超时、限流等。

#### ModelConfig

记录模型展示名、实际模型名、provider 绑定、默认参数、启停状态。

#### RoleBinding

记录评分老师、评分审核、最终评判分别绑定哪个 ModelConfig。

通过这种抽象，系统可以在不改变评分流程的情况下切换模型名、Provider 或角色映射。

## 9. 多模型编排与仲裁规则

### 9.1 标准编排链路

1. 评分老师模型基于统一量表给出主评分结果。
2. 评分审核模型在不共享主评分结果的前提下独立复核。
3. 系统程序化比较两份结果。
4. 如命中分歧规则，触发最终评判模型仲裁。
5. 合成最终结果并写入快照。

### 9.2 分歧检测规则

一期至少检测以下三类分歧：

1. 总分差异超过阈值，例如超过 15%。
2. 关键维度分差超过阈值，例如某核心维度差异超过 20%。
3. 致命错误判定冲突，例如一个模型命中致命错误，另一个未命中。

### 9.3 仲裁输入

仲裁模型输入必须包含：

1. 题目与学生答案。
2. 评分量表与评分规则。
3. 两份独立评分结果。
4. 系统生成的冲突摘要。

仲裁模型职责不是简单重评，而是对冲突点作出明确裁决并形成最终结论。

### 9.4 最终结果合成策略

1. 无冲突时，默认采用两份评分的加权平均，并保留各自明细。
2. 有冲突时，以仲裁结果为准。
3. 命中致命错误时，不直接自动定档，而是必须进入仲裁。

本期推荐使用“无冲突加权平均，有冲突由仲裁定夺”的策略，以平衡稳定性和可信度。

## 10. 题型差异化评分策略

### 10.1 统一原则

不同题型共用同一外层编排框架，但使用不同的评分上下文装配器。系统不采用“一套 Prompt 评分所有题型”的策略。

推荐设计两个 RubricBuilder：

1. `CodeRubricBuilder`
2. `ShortAnswerRubricBuilder`

开放题后续可扩展为新的 Builder。

### 10.2 代码题策略

代码题评分遵循“功能正确性优先由可执行证据支撑，AI 负责解释与补充判断”的原则。

代码题证据分三层：

1. 静态代码证据，包括代码完整性、语法可解析性、可读性、异常处理、规范性。
2. 动态执行证据，包括编译结果、测试通过率、失败摘要、运行错误、超时和资源超限情况。
3. 语义与工程证据，包括算法思路、复杂度合理性、结构设计和可维护性。

代码题评分输入除题目和代码外，还应包含：

1. 语言信息。
2. 执行环境。
3. 测试摘要。
4. 编译与运行结果。
5. 日志摘要。

代码题特殊规则：

1. 功能正确性维度的得分上限应受测试通过率约束。
2. 编译失败应直接触发降档规则，并进入高风险状态。
3. 程序性致命错误和业务性致命错误分开建模。
4. 任一模型命中致命错误时必须进入仲裁，而非直接定分。

### 10.3 简答题策略

简答题评分遵循“知识点覆盖加语义对齐加结构表达”的原则，而不是仅做关键词命中。

简答题评分依据应至少包含：

1. 知识点清单及权重。
2. 每个知识点的说明和可接受表达示例。
3. 反向扣分项，例如概念混淆、因果倒置、关键结论错误。
4. 表达与结构维度，例如逻辑性、完整性、准确性。

简答题评分输出应明确说明：

1. 命中了哪些知识点。
2. 缺失了哪些知识点。
3. 哪些表达虽然措辞不同但语义可接受。
4. 哪些内容属于实质性理解错误。

## 11. 人工干预设计

### 11.1 人工干预类型

一期支持以下三种人工动作：

1. 重评。
2. 改分。
3. 补评语。

### 11.2 人工重评

人工重评允许在调整评分重点、Prompt 模板或角色绑定后重新触发评分流程。重评生成新的任务或新的结果快照，不覆盖旧结果。

### 11.3 人工改分

人工可以直接修改最终分数或某个维度分，但系统必须要求填写改分原因。改分动作生成新的人工快照，并保留 AI 原始结果。

### 11.4 人工补评语

人工可以修改面向学生展示的评语，但必须保留原 AI 评语和修改记录。

### 11.5 基本约束

1. AI 原始结果不可删除。
2. 人工结果不可静默替换原结果。
3. 所有人工动作都必须留痕。

## 12. 最终报告结构

建议定义统一的 `FinalGradingReport`，至少包含以下部分：

### 12.1 基础信息

1. 题目 ID。
2. 任务 ID。
3. 题型。
4. 满分。
5. 最终得分。
6. 评分状态。
7. 是否人工干预。

### 12.2 维度评分

1. 每个维度的得分。
2. 权重。
3. 评分依据。
4. 扣分原因。

### 12.3 证据摘要

1. 代码题显示测试通过率、运行状态、失败摘要。
2. 简答题显示知识点命中、缺失点和误区点。

### 12.4 模型链路

1. 参与的角色。
2. 使用的模型。
3. 使用的 Provider。
4. 是否触发仲裁。
5. 仲裁触发原因。

### 12.5 风险与置信提示

1. 模型一致性高或低。
2. OCR 低置信片段。
3. 致命错误待确认或已确认。

### 12.6 反馈内容

1. 优点分析。
2. 主要问题。
3. 改进建议。

反馈建议拆分为教师可见版和学生可见版，避免内部判断细节被直接暴露给学生。

### 12.7 人工处理记录

1. 是否人工改分。
2. 改分前后差异。
3. 操作人。
4. 原因。
5. 时间。

## 13. 审计规则

系统应将以下动作记录为标准审计事件：

1. 任务创建。
2. 模型调用。
3. 规则触发。
4. 结果确认。
5. 人工操作。
6. 配置变更。

审计设计的目标是支持以下问题追溯：

1. 为什么这道题得到当前分数。
2. 为什么同一答案不同时间评分结果不同。
3. 差异来自模型变化、规则变化还是人工干预。

## 14. 对外接口建议

本期不展开 API 详细字段设计，但建议至少形成以下接口边界：

1. 创建评分任务接口。
2. 查询评分任务状态接口。
3. 查询评分快照列表接口。
4. 查询最终评分报告接口。
5. 触发人工重评接口。
6. 提交人工改分接口。
7. 查询审计事件接口。

这些接口应同时服务单题调试台和批量阅卷任务中心。

## 15. 一期验收标准

当以下条件成立时，可认为“评分编排与可信度内核”达到一期目标：

1. 能对代码题和简答题创建统一评分任务并完成评分。
2. Qwen、DeepSeek、Claude 三个角色模型可以按配置执行，其中 Claude 通过 OpenRouter 接入。
3. 系统可程序化识别模型间分歧并触发仲裁。
4. 代码题能接收沙箱和单测结果作为高优先级评分证据。
5. 系统能输出统一的结构化最终评分报告。
6. 系统支持人工重评、改分和补评语，并完整留痕。
7. 系统可以追踪一次评分所使用的模型配置、角色绑定和 Prompt 模板版本。

## 16. 后续子项目衔接

在本设计落地后，后续两个子项目可以围绕本期内核继续展开：

1. 采集与导入层负责将 OCR、图片、文件和考试系统结果规范化为评分任务输入。
2. 阅卷工作台与调优台负责呈现任务状态、结果对比、人工复核和 Prompt 调优能力。

这两个子项目都不应绕过当前定义的评分任务、结果快照和审计结构，而应直接复用本期内核能力。
