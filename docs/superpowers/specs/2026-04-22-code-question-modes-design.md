# 代码题模式设计

## 背景

当前系统中的代码题默认更接近“函数题 / LeetCode 风格”：

- 题目内容中存在 `function_name`、`signature`、`starter_code`
- 学生端会展示函数签名与平台预置模板
- 在线运行以 `sample_tests` 为基础，但题目模型默认没有把“完整程序题”和“函数题”严格区分

这带来了两个核心问题：

1. 对学生不友好。当前默认模板如 `class Solution`、`self, *args` 对大部分考生来说并不直观，学生很难理解平台会如何传参、自己到底应该实现什么。
2. 对平台语义不清。题目内容里同时混有“函数签名”“示例输入输出”“多语言模板”等信息，但没有明确的模式边界，导致在线运行、正式判题和题目展示都容易混乱。

用户已经明确给出产品方向：

- 站在学生视角，默认代码题应为“完整程序题”
- 函数题仍可保留，但应作为高级模式，而不是默认路径
- 对于完整程序题，用例应采用“输入 / 期望输出”的经典模型

本设计的目标，是把代码题产品模型收敛成清晰的双模式结构，并使默认体验回归完整程序题。

## 目标

### 功能目标

- 新建代码题默认使用“完整程序题（Program Mode）”
- 保留“函数题（Function Mode）”，但作为高级模式显式切换
- 学生端默认看到完整程序题，不再默认面对函数签名和平台调用规则
- 在线运行与后续正式判题的主路径统一围绕 `stdin -> stdout`
- 对旧题保持兼容，不做破坏性迁移

### 非目标

- 不在本阶段彻底重写已有函数题执行器
- 不在本阶段支持任意复杂对象的跨语言参数注入
- 不在本阶段强制迁移历史代码题数据

## 用户与使用场景

### 学生

学生默认期望的是：

- 看懂题意
- 明白输入是什么
- 明白输出应该是什么
- 直接写程序并运行

默认代码题不应要求学生猜测：

- 平台会如何调用函数
- `*args` 里到底会传几个参数
- 自己是否要处理输入读取

### 教师

教师的真实需求分为两类：

1. 主流场景：发布标准输入 / 标准输出型编程题，考察算法思路、逻辑组织、代码正确性
2. 高级场景：只考函数核心逻辑，不希望学生处理输入输出，这时需要函数题

因此平台应满足：

- 普通教师默认用最简单的完整程序题
- 熟悉该模式的高级教师可以主动切换为函数题

## 方案对比

### 方案 A：只保留完整程序题

优点：

- 学生最容易理解
- 在线运行与正式判题最统一
- 测试用例天然就是 `input / expected_output`
- 产品模型最简单

缺点：

- 对只想考函数逻辑的教师不够灵活

### 方案 B：完整程序题为默认，函数题作为高级模式

优点：

- 满足默认学生体验
- 兼顾高级教师的函数题需求
- 平台可以把复杂度限制在高级模式中
- 迁移成本可控

缺点：

- 后台建题表单会多一个模式切换
- 平台需要维护两种题目元数据结构

### 方案 C：继续以函数题为主，只优化模板

优点：

- 变更最少

缺点：

- 没有解决根因
- 学生仍需理解平台传参语义
- `self, *args` 等问题仍会反复出现

### 结论

采用方案 B：

- 默认代码题 = 完整程序题
- 函数题 = 高级模式

## 总体设计

代码题引入明确的模式字段：

- `program`：完整程序题，默认模式
- `function`：函数题，高级模式

系统中的学生端展示、在线运行、正式判题和后台建题都优先围绕 `program` 构建。

### 核心原则

- 默认模式必须让学生“一眼就懂”
- 高级模式必须让规则“明确且完整”
- 平台不再用混合字段隐式推断题目语义

## 学生端体验设计

### 完整程序题（默认）

学生页面固定围绕以下结构展示：

- 题目描述
- 输入说明
- 输出说明
- 示例输入 / 示例输出
- 数据范围（可选）

编辑器中学生写的是完整程序，不默认展示：

- `function_name`
- `signature`
- `class Solution`
- `self, *args`

在线运行行为：

- 示例测试：平台把 `sample_tests[].input` 作为标准输入，比较标准输出与期望输出
- 自定义测试：学生填写自定义输入，平台展示运行输出

学生的心智模型应统一为：

- “我写完整程序”
- “系统把输入喂给程序”
- “程序输出与期望输出比较”

### 函数题（高级模式）

学生页面必须明确标识当前是函数题，并显式展示：

- 函数名
- 参数列表
- 返回值要求
- 平台调用方式说明

示例展示不再使用“示例输入 / 示例输出”的 OJ 术语，而应使用：

- 输入参数
- 返回结果

这类题目只适用于教师明确知道自己要考“函数实现逻辑”的场景。

## 教师端建题体验设计

### 默认模式：完整程序题

教师新建编程题时，默认进入“完整程序题（推荐）”模式。

表单默认展示：

- 题目描述
- 输入说明
- 输出说明
- 数据范围（可选）
- 示例输入 / 示例输出
- 测试用例（输入、期望输出）
- 多语言起始代码（可选）

默认情况下，不展示：

- `function_name`
- `signature`
- 参数类型
- 返回值类型

如果教师不填写模板，学生端允许直接从空白完整程序开始作答。

### 高级模式：函数题

教师主动切换到“函数题（高级）”后，才展开额外字段：

- 函数名
- 参数列表
- 参数类型
- 返回值类型
- 多语言函数模板
- 参数型测试用例

界面中应明确提示：

- 该模式适合只考函数核心逻辑
- 平台会根据参数定义自动调用学生函数

### 模式切换规则

- 代码题表单顶部新增“作答模式”
- 默认选中 `完整程序题（推荐）`
- 函数题切换后显示高级字段
- 教师切回完整程序题时，不立即删除高级字段内容，但默认隐藏

## 数据结构设计

### 完整程序题

建议的 `question.content` 结构：

```json
{
  "mode": "program",
  "description": "...",
  "input_description": "...",
  "output_description": "...",
  "constraints": ["..."],
  "examples": [
    {
      "input": "1 2",
      "output": "3",
      "explanation": "..."
    }
  ],
  "sample_tests": [
    {
      "name": "示例 1",
      "input": "1 2",
      "expected_output": "3",
      "is_public": true
    }
  ],
  "starter_code": {
    "python": "",
    "javascript": "",
    "java": "",
    "cpp": "",
    "c": "",
    "go": ""
  }
}
```

说明：

- `mode = "program"` 明确说明是完整程序题
- `sample_tests` 语义是 `stdin -> stdout`
- `starter_code` 为可选增强，不再是平台强制要求的框架

### 函数题

建议的 `question.content` 结构：

```json
{
  "mode": "function",
  "description": "...",
  "function_name": "twoSum",
  "parameters": [
    { "name": "nums", "type": "int[]" },
    { "name": "target", "type": "int" }
  ],
  "return_type": "int[]",
  "constraints": ["..."],
  "examples": [
    {
      "args": [[2, 7, 11, 15], 9],
      "output": "[0,1]",
      "explanation": "..."
    }
  ],
  "sample_tests": [
    {
      "name": "示例 1",
      "args": [[2, 7, 11, 15], 9],
      "expected_output": "[0,1]",
      "is_public": true
    }
  ],
  "starter_code": {
    "python": "def twoSum(nums, target):\n    pass",
    "javascript": "function twoSum(nums, target) {\n}",
    "java": "...",
    "cpp": "...",
    "c": "...",
    "go": "..."
  }
}
```

说明：

- `function` 模式下，测试用例不再是 `input`
- 统一改为结构化 `args`
- 平台需基于参数列表和返回值定义进行调用与序列化

## 在线运行与正式判题规则

### 完整程序题

这是后续在线运行和正式判题的主路径。

规则：

- 平台将 `sample_tests[].input` 写入标准输入
- 执行学生完整程序
- 采集标准输出
- 与 `expected_output` 对比

优点：

- 语义清晰
- 与多数在线判题系统一致
- 最适合当前平台默认体验

### 函数题

函数题不再使用不透明的 `self, *args` 风格。

平台必须：

- 根据 `parameters` 和 `sample_tests[].args` 生成语言对应的调用包装
- 调用学生实现的目标函数
- 将返回值序列化成稳定输出
- 与期望结果比较

为控制复杂度，第一阶段函数题仅支持受限类型：

- 基础标量：整数、浮点数、布尔、字符串
- 一维数组
- 二维数组

不支持任意复杂对象、图结构、树节点等高级类型。

### 优先级策略

第一阶段应先做稳完整程序题：

- 在线运行以 `program` 模式为主
- 正式判题以 `program` 模式为主
- `function` 模式保留数据结构和产品入口，但执行链路可以分阶段完善

## 兼容策略

为避免破坏已有题目，采用向后兼容方案。

### 老题兼容规则

- 没有 `mode` 的旧题目，先按旧逻辑兼容
- 如果题目中存在 `function_name` / `signature` 等典型字段，则优先视为旧函数题
- 新建题目一律显式写入 `mode`

### 学生端兼容规则

- 学生端优先读取 `mode`
- 若无 `mode`，则 fallback 旧结构
- 旧函数题仍可显示，但默认新题不再使用旧模板模型

### 数据迁移策略

- 本阶段不强制迁移历史数据
- 可在后续提供后台批量升级工具，将旧函数题迁移为新 `function` 结构

## 分阶段落地顺序

### 第一阶段：产品模型收敛

- 后台建题支持模式切换
- 默认模式改为 `program`
- 新题显式写入 `mode`
- 学生端优先识别 `mode`

### 第二阶段：完整程序题主路径打通

- 学生端展示完整程序题结构
- 在线运行与正式判题统一使用 `stdin/stdout`
- 结果展示与测试用例展示围绕输入输出构建

### 第三阶段：高级函数题完善

- 参数类型系统
- 多语言调用包装
- `args` 型测试用例
- 受限类型序列化与比较规则

## 风险与约束

### 风险 1：模式混用导致复杂度上升

应对：

- 默认路径只强调完整程序题
- 函数题明确标记为高级模式

### 风险 2：旧题兼容期逻辑分叉

应对：

- 新老结构的判定规则必须集中实现
- 避免在多个页面重复写兼容判断

### 风险 3：函数题执行链复杂

应对：

- 函数题不抢占第一阶段主路径
- 限制支持的参数类型范围

## 最终结论

代码题应明确区分两种模式：

- 默认：完整程序题
- 高级：函数题

平台默认学生体验应统一为：

- 写完整程序
- 平台提供输入
- 平台比较输出

当前的 `self, *args` 与隐式函数调用模型不应继续作为默认路径存在，而应逐步退出默认体验，仅在高级函数题场景中通过更明确的数据结构和规则保留。
