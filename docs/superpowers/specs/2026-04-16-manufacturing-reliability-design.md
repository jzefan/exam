# 制造业可靠性 MIITEC 导入设计

## 背景

当前仓库已经形成一条可复用的 MIITEC 标准岗位模型接入链路：

1. 从 PDF 提取岗位与能力结构化信息
2. 生成 `backend/scripts/data/extracted/*.json` 中间结果
3. 映射为 `backend/scripts/data/templates/*.json` 导入模板
4. 通过 `backend/scripts/import_standard_models.py` 导入数据库
5. 做二次导入幂等验证、关键回归测试与报告更新

现有已覆盖的批次包括：IC / 大数据 / 数据标注 / AI 八方向 / 生物医药 / 新材料。下一步是在完全复用这条成熟流程的前提下，把 `docs/miitec_pdfs/《制造业可靠性人才岗位能力要求》` 纳入同一套提取、模板、导入与验证体系。

本次工作的目标不是重构整套提取器，而是以最小改动把“制造业可靠性”行业平稳接入现有链路，并保持与前述批次一致的验证标准和报告口径。

## 目标

将《制造业可靠性人才岗位能力要求》接入现有 MIITEC 标准岗位模型流程，形成：

- 一个可复现的结构化提取结果
- 一个可导入的模板 JSON
- 一次成功导入与一次幂等导入验证
- 一组关键 backend / frontend 回归验证结果
- 两份同步更新的 MIITEC 报告

## 非目标

本次设计明确不包含以下内容：

- 不重构 `backend/scripts/extract_pdfs_intelligent.py` 的整体架构
- 不修改 `backend/scripts/import_standard_models.py` 的既有导入语义，除非发现无法接入的真实契约问题
- 不对其他尚未纳入流程的 PDF 做完成性声明
- 不顺带清理或统一历史报告格式，只在现有格式上补充“制造业可靠性”批次

## 推荐方案

采用“在现有提取器中直接新增行业配置”的方案。

### 方案对比

#### 方案 1（推荐）：扩展现有提取配置

在 `backend/scripts/extract_pdfs_intelligent.py` 的现有 `pdf_configs` 中新增“制造业可靠性”条目，沿用当前已验证的分块提取、模型调用、输出结构和中间产物目录。

优点：
- 改动最小，和“新材料”等前序工作保持一致
- 最容易做导入、幂等和回归验证
- 失败面最小，便于快速定位问题

缺点：
- 提取脚本会继续增长
- 结构层面的可维护性问题继续保留

#### 方案 2：一次性脚本单独提取

为“制造业可靠性”单独写一次性提取脚本，再手工映射模板。

优点：
- 隔离度高

缺点：
- 容易偏离现有标准流程
- 后续复用性和可维护性差
- 报告和验证链路更容易出现分叉

#### 方案 3：先重构再接入

先把提取器重构成更模块化的配置/插件结构，再新增“制造业可靠性”。

优点：
- 长期结构更好

缺点：
- 明显超出当前范围
- 风险、工作量和验证成本更高
- 不符合“按同样思路和分析方法继续”的当前目标

### 结论

本次采用方案 1。理由是：当前目标是把新增 PDF 平稳纳入既有流程，而不是借机改造基础设施。最小改动最符合范围控制，也最利于验证与回归。

## 数据流设计

### 1. PDF 提取

系统读取 `docs/miitec_pdfs/《制造业可靠性人才岗位能力要求》`，沿用当前提取器中已经验证过的文本提取和分块策略，抽取岗位、方向、能力要求等结构化内容。

该阶段的输出必须保持与既有提取文件一致的基本契约：

- 包含 `metadata`
- 包含 `models`
- `metadata` 内包含来源、行业、版本说明、模型类型等字段

行业名统一使用：`制造业可靠性`

### 2. 结构化结果落盘

提取结果写入：

- `backend/scripts/data/extracted/manufacturing_reliability_complete.json`

这个阶段的目标是把模型输出固化成可检查的结构化文件，便于后续发现“岗位缺失、字段不全、结构错误”等问题时先在提取层止损，而不是直接进入模板层。

### 3. 模板映射

将结构化提取结果映射为最终模板：

- `backend/scripts/data/templates/manufacturing_reliability.json`

模板结构必须满足现有 importer 预期，不引入新的字段协议，不修改既有导入契约。

### 4. 静态校验

在导入前，必须完成以下校验：

- 占位词检查：不得出现 `TODO`、`待补充`、`placeholder`、`占位`
- JSON 语法校验：模板文件必须能通过标准 JSON 解析
- 必要时做基本结构检查：确认顶层结构和关键字段存在

### 5. 数据库导入

通过：

- `backend/scripts/import_standard_models.py`

导入 `manufacturing_reliability.json`。

第一次导入的目标是成功写入新行业对应岗位模型；第二次导入的目标是验证幂等，不重复创建。

### 6. 幂等验证

再次导入同一模板，预期结果是：

- `Created 0, skipped N`

其中 `N` 应与该文件中实际岗位条目数一致。

### 7. 回归验证

运行与 job models 相关的关键 backend / frontend 测试，确认新增行业不会破坏标准库、快创流程和相关服务逻辑。

### 8. 报告更新

仅在提取、导入、幂等和关键测试已真实完成的前提下，更新两份 MIITEC 报告。

## 错误处理策略

### PDF 提取失败

如果出现以下问题：

- PDF 文本提取为空
- 页面文本抽取异常
- 输出结构缺失关键部分

则流程停在提取阶段，不继续生成模板或执行导入。先修正提取输入或提取逻辑，再继续后续步骤。

### 模型输出不完整或结构错误

如果提取后的结构化 JSON 出现岗位缺失、字段层级不正确或内容明显截断，则先修正提取/映射逻辑，不允许绕过中间文件审查直接手工拼接导入模板。

### 导入失败

如果 importer 报错，优先判断：

- 模板字段是否符合既有契约
- 行业名、模型类型、岗位结构是否符合 importer 预期
- 是否有数据格式问题导致去重或写库失败

除非确认 importer 无法兼容既有模板协议，否则不在本轮顺手修改 importer 语义。

### 回归失败

若 backend 或 frontend 关键测试失败，先判断是否由本次新增行业引入：

- 若是本次变更导致，修复后再继续
- 若是既有基线不稳定，需要在报告与总结中明确区分，不把无关失败误记为本次功能已完成

## 测试与验证策略

### 导入验证

验证标准包括：

1. 首次导入成功
2. 二次导入幂等
3. 可统计出“制造业可靠性”行业导入后的岗位数量

### 后端验证

以现有 `job_models` 关键测试为主，确认新增模板与导入逻辑不会破坏服务层、路由层和快创相关逻辑。

### 前端验证

以标准库页面与快创页面的关键测试为主，确认前端消费标准岗位模型时未受影响。

### 文档验证

报告中的所有描述都必须和实际执行结果一致：

- 已运行的命令才写入报告
- 已验证的幂等结果才写入报告
- 已确认的数量才写入报告
- 不做超出本次范围的完成性声明

## 边界与完成定义

本次工作完成的标准是：

1. `extract_pdfs_intelligent.py` 成功接入“制造业可靠性”配置
2. 成功生成 `manufacturing_reliability_complete.json`
3. 成功生成 `manufacturing_reliability.json`
4. 模板通过占位词与 JSON 语法校验
5. 模板可成功导入数据库
6. 二次导入验证幂等
7. 关键 backend / frontend 测试通过
8. `docs/MIITEC_import_report.md` 与 `docs/MIITEC_extraction_final_report.md` 完成更新

若上述任一项未完成，则报告必须按真实范围表述，不得把“制造业可靠性”写成已完整闭环完成。

## 设计总结

本设计的核心原则是：完全复用现有成熟链路，以最小改动接入《制造业可靠性人才岗位能力要求》，并用与前序批次相同的验证标准收口。这样既能保证一致性，也能把风险控制在单一行业扩展的范围内。
