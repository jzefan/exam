# 教师侧数据可见性与共享设计

日期：2026-04-11

## 1. 背景

当前平台支持多个教师账号，但数据访问仍主要依赖角色权限，缺少明确的数据归属与共享规则。这会带来两个问题：

1. 教师默认可能看到不属于自己的业务数据。
2. 即使产品要求“题库和知识点可共享、考试和学生绝对私有”，后端也没有统一的数据权限模型来保证这一点。

本设计的目标是在“单平台、多教师、无组织概念”的前提下，引入一套统一的数据级权限方案。

## 2. 设计目标

本次设计只解决教师侧业务数据的可见性与共享，不调整现有平台管理员的全局管理职责。

目标如下：

1. 教师创建的数据默认私有。
2. 只有题库和知识点允许共享给平台内所有教师。
3. 考试和学生及其衍生数据永远私有。
4. 平台管理员可查看和管理全部数据。
5. 权限规则统一沉淀到后端查询与写操作校验中，前端只做展示与交互，不承担安全职责。

## 3. 业务边界

### 3.1 平台角色

本设计只区分两类关键主体：

1. 平台管理员 `platform_admin`
2. 非平台管理员教师 `teacher`

### 3.2 资源分类

按照共享规则，将资源分为两类：

允许平台公开：

1. 题库 `question_banks`
2. 知识点 `knowledge_points`

永远私有：

1. 学生
2. 考试
3. 考试关联学生
4. 学生答卷
5. 阅卷记录
6. 成绩申诉
7. 教师私有统计数据

### 3.3 题目规则

题目本身不单独配置公开状态，而是跟随所属题库的可见性：

1. 教师自己的题目可见。
2. 其他教师题库若为平台公开，则该题库下题目对教师只读可见。
3. 若题目未归属任何题库，则仅创建者本人和平台管理员可见。

该规则优先保证一致性，避免出现“题库公开但部分题目不可见”或“题目公开但题库私有”的不一致状态。

## 4. 核心模型

### 4.1 数据归属字段

所有教师侧业务数据都需要具备归属概念。建议统一引入：

- `owner_id: UUID not null`

语义：该资源当前归属于哪位教师，用于数据权限判断。

注意：

- `owner_id` 不能直接等价于 `created_by`
- `created_by` 是审计字段
- `owner_id` 是权限字段

本期即使两者初始值相同，也应保留语义分离，便于未来支持转移归属、模板复制等场景。

### 4.2 可见性字段

仅对允许共享的资源增加：

- `visibility: VARCHAR(20) not null default 'private'`

枚举值：

1. `private`
2. `platform`

含义：

- `private`: 仅 owner 和平台管理员可见
- `platform`: 平台内所有教师和平台管理员可见

## 5. 各资源的数据模型调整

### 5.1 题库

表：`question_banks`

新增字段：

1. `owner_id`
2. `visibility`

默认值：

- `owner_id = 当前教师`
- `visibility = 'private'`

### 5.2 知识点

当前知识点模型存在两处上下文：

1. `backend/src/app/learning/models.py` 中的知识点主模型
2. `backend/src/app/questions/router.py` 中对知识点接口的兼容访问

本期应以 `app.learning` 中的知识点主模型为准，为知识点主表新增：

1. `owner_id`
2. `visibility`

### 5.3 题目

表：`questions`

新增字段：

1. `owner_id`

保留现有：

1. `created_by`
2. `question_bank_id`

规则：

1. 题目默认 `owner_id = 当前教师`
2. 题库内题目以题库可见性为准
3. 无题库题目仅本人可见

### 5.4 考试

表：`exams`

当前已有 `created_by`。本期建议新增：

1. `owner_id`

不新增 `visibility`。

### 5.5 学生

学生管理当前落在 RBAC 体系内，已有组织相关结构，但本期产品设定中暂不启用组织隔离。实现时需要在学生实体或教师与学生关系表上体现归属教师。

要求：

1. 每个学生必须归属某位教师
2. 只有归属教师和平台管理员可见
3. 不允许公开

由于当前学生结构与 `UserOrganization`、`Class` 等实现耦合，本期实施时可采用“新增教师归属字段”或“新增教师-学生关联表”两种路径，最终方案由实施阶段根据现有表结构确定，但权限语义必须保持一致。

## 6. 读取权限规则

### 6.1 平台管理员

平台管理员对所有资源拥有全量可见权限：

1. 查看全部
2. 编辑全部
3. 删除全部
4. 修改共享状态

### 6.2 教师

教师读取规则如下：

#### 学生

只能查看自己的学生：

- `owner_id = current_user.id`

#### 考试

只能查看自己的考试：

- `owner_id = current_user.id`

#### 题库

可查看：

1. 自己的题库
2. 平台公开题库

查询逻辑：

- `owner_id = current_user.id OR visibility = 'platform'`

#### 知识点

可查看：

1. 自己的知识点
2. 平台公开知识点

查询逻辑：

- `owner_id = current_user.id OR visibility = 'platform'`

#### 题目

可查看：

1. 自己的题目
2. 平台公开题库中的题目

查询逻辑建议优先通过题库联表控制，而不是只看题目自身字段。

## 7. 写权限规则

教师对资源的写操作必须同时满足：

1. 角色允许该类操作
2. 该资源归属于当前教师

因此：

### 7.1 教师可操作

1. 创建自己的题库、题目、知识点、考试、学生
2. 更新自己的题库、题目、知识点、考试、学生
3. 删除自己的题库、题目、知识点、考试、学生
4. 修改自己题库、知识点的 `visibility`

### 7.2 教师不可操作

1. 修改其他教师公开的题库
2. 删除其他教师公开的题库
3. 修改其他教师公开的知识点
4. 删除其他教师公开的知识点
5. 查看或修改其他教师的考试、学生及其衍生数据

结论：

公开资源对其他教师仅只读，不共管。

## 8. 后端实现约束

### 8.1 权限判断必须落在后端

前端只负责展示，不可信任。所有列表、详情、更新、删除接口都必须在后端执行资源级过滤与校验。

### 8.2 推荐收口方式

在后端抽出统一的数据权限助手，而不是让各模块重复写条件判断。

建议至少提供以下能力：

1. `is_platform_admin(user)`
2. `apply_teacher_visibility_filter(query, model, user, resource_type)`
3. `ensure_can_read_resource(user, resource)`
4. `ensure_can_write_resource(user, resource)`
5. `ensure_can_change_visibility(user, resource)`

### 8.3 路由层责任

每个 router 只做三件事：

1. 读取当前用户
2. 调用 service 层查询
3. 在详情、更新、删除时调用统一权限校验函数

不要在每个路由里临时拼装不同版本的权限逻辑。

## 9. 模块改造范围

### 9.1 Questions 模块

涉及文件：

1. `backend/src/app/questions/models.py`
2. `backend/src/app/questions/service.py`
3. `backend/src/app/questions/router.py`
4. `backend/src/app/questions/schemas.py`

改造内容：

1. 为题库、题目接入 `owner_id`
2. 为题库接入 `visibility`
3. 列表接口按可见性过滤
4. 详情、更新、删除接口按 owner 校验
5. 返回值中增加可见性与归属信息，供前端显示只读态

### 9.2 Learning 模块

涉及文件：

1. `backend/src/app/learning/models.py`
2. `backend/src/app/learning/service.py`
3. `backend/src/app/learning/router.py`
4. 兼容知识点输出的相关 schema/router

改造内容：

1. 为知识点接入 `owner_id`
2. 为知识点接入 `visibility`
3. 列表与详情读取按可见性过滤
4. 更新、删除、前置依赖维护等写操作按 owner 校验

### 9.3 Exams 模块

涉及文件：

1. `backend/src/app/exams/models.py`
2. `backend/src/app/exams/service.py`
3. `backend/src/app/exams/router.py`

改造内容：

1. 为考试明确 `owner_id`
2. 列表和详情严格限制为 owner 或平台管理员
3. 阅卷、答卷、申诉等衍生查询继承考试私有规则

### 9.4 Students / RBAC 模块

涉及文件：

1. `backend/src/app/rbac/students_router.py`
2. `backend/src/app/rbac/service.py`
3. 学生归属对应的模型定义

改造内容：

1. 将当前“按组织查询学生”调整为“按教师归属查询学生”
2. 平台管理员保留全量管理能力
3. 教师只能管理自己名下学生

## 10. 前端约束

前端不负责权限兜底，但需要正确表达状态。

### 10.1 题库与知识点

对教师自己的资源显示可切换状态：

1. 私有
2. 平台公开

对其他教师公开的资源显示：

1. `平台公开`
2. 来源教师信息
3. 只读态

### 10.2 考试与学生

前端不提供任何共享入口。

## 11. 兼容与迁移

### 11.1 历史数据回填

历史数据迁移规则建议如下：

1. 已有题目：`owner_id = created_by`
2. 已有考试：`owner_id = created_by`
3. 已有题库：若缺少创建人字段，需根据关联题目创建人或业务规则补齐；补齐前不得上线权限过滤
4. 已有知识点：若历史上无创建人概念，需根据导入人、维护人或统一管理员归属策略补齐
5. 所有支持共享的历史资源默认 `visibility = 'private'`

### 11.2 上线安全策略

上线顺序必须保证先完成数据回填，再启用读取过滤。否则会出现资源丢失或越权暴露。

## 12. 非目标

本期不做以下能力：

1. 指定教师共享
2. 协同共管
3. 组织维度隔离
4. 公开资源复制副本
5. 面向学生的数据共享

## 13. 测试要求

至少覆盖以下场景：

1. 教师只能看到自己的学生
2. 教师只能看到自己的考试
3. 教师能看到自己的私有题库
4. 教师能看到其他教师的平台公开题库
5. 教师不能编辑其他教师的平台公开题库
6. 教师能看到其他教师的平台公开知识点
7. 教师不能编辑其他教师的平台公开知识点
8. 教师无法看到其他教师私有考试
9. 平台管理员可查看全部
10. 历史数据回填后，默认共享状态为私有

## 14. 推荐实施顺序

1. 增加字段与迁移脚本
2. 回填历史数据
3. 接入后端读取过滤
4. 接入后端写权限校验
5. 暴露前端只读态与共享开关
6. 补充自动化测试

## 15. 结论

本方案将平台内教师数据权限定义为：

1. 默认私有
2. 题库和知识点可平台公开
3. 考试和学生绝对私有
4. 公开仅代表可读，不代表共管
5. 数据权限以 `owner_id + visibility + platform_admin` 三元规则统一收口

该方案满足当前产品边界，同时为未来扩展“指定教师共享”保留了清晰升级路径。
