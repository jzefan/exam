# Word 题目导入与页面图片兜底设计

日期：2026-05-10

## 1. 背景

当前题目导入已经支持 `pdf / docx / md` 文档识别，并且具备：

- 前端文件解析与上传
- 后端规则分题与规则判型
- 导入前逐题校对
- 低置信度问题的 AI 补全

但 `docx` 在真实教师文档里仍存在一个关键问题：选择题经常只能识别出题干，选项丢失。用户提供的样例表明，题目正文中的阿拉伯题号可以被识别，但 A/B/C/D 选项没有进入识别结果，导致系统把多道单选题错误地识别成只有题干的短答题草稿。

根因不是单点 bug，而是当前 `docx` 导入链路在“前端文本抽取”和“后端选项识别”之间存在结构信息丢失：

- 前端 `htmlToImportText` 会把 Word 有序列表统一降级成 `- xxx`
- 后端规则只把 `A.` / `A、` / `A)` 这类显式字母前缀识别为选项
- 当 Word 里的选项本来是自动编号列表而不是正文字符时，选项语义会在进入后端前被抹平

本设计的目标不是重写整套导入系统，而是在尽量小的改动范围内修复 `docx` 选择题识别质量，并为复杂版式增加“页面图片识别”兜底路径。

## 2. 目标

### 2.1 功能目标

- 修复 `docx` 导入时选择题选项丢失的问题。
- 同时支持两类常见来源：
  - 选项本来就是正文字符的 `A./B./C./D.` 文本题目
  - 选项来自 Word 自动编号/项目编号的列表题目
- 保持现有按题号分题、按题型继承大题类型、导入前审核的流程不变。
- 在文本链路识别质量明显不足时，支持按页面图片送后端识别作为兜底。

### 2.2 非目标

- V1 不替换现有文本识别主路径。
- V1 不做通用高保真 Word 版面还原。
- V1 不保证复杂表格、浮动文本框、跨页公式全部结构化正确。
- V1 不把“页面图片识别”作为所有 `docx` 的默认流程。

## 3. 设计原则

### 3.1 文本解析仍然是主路径

对本身可提取文本的 `docx`，优先走现有 `docx -> HTML -> 导入文本 -> 后端分题` 链路。文本路径成本更低、速度更快、可解释性更强，也更容易调试和回归测试。

### 3.2 修根因，不只补症状

当前问题的核心不是“后端少写了一个正则”，而是前端在抽取 Word HTML 时丢失了列表语义。方案必须同时修复：

- 前端不要把不同类型列表一律抹平成普通短横线
- 后端要能在保留现有显式选项规则的前提下，识别结构化列表选项

### 3.3 兜底路径只在必要时触发

页面图片识别适合处理复杂版式，但代价更高。它应当是文本链路的 fallback，而不是默认主路线。

### 3.4 所有结果都进入人工审核

无论来自文本识别还是页面图片识别，识别结果都必须进入现有 review 流程。系统可以提高初始识别质量，但不跳过老师确认。

## 4. 问题边界

本次设计只处理“题目边界已经大致可分，但题目内部选项没有被正确保留或识别”的问题，不重写整套分题机制。

继续沿用现有能力：

- `segment_question_document` 负责按题号、大题标题、题型提示切分题目
- `preprocess_paper_import_text` 负责清洗试卷封面、题型标题等噪声
- `build_import_draft_from_segment` 负责从单题块提取题干、选项、答案、解析、难度

重点增强的是“单题块内部的结构保真”和“选择题选项提取”。

## 5. 总体方案

采用双层方案：

1. **主路径：增强 docx 文本链路**
   - 前端在导出导入文本时保留列表类型语义
   - 后端在构建单题草稿时识别显式选项和隐式列表选项

2. **兜底路径：页面图片识别**
   - 当文本链路识别结果质量明显不足时，允许走页面图片识别
   - 图片识别结果仍映射回同一套 `QuestionImportDraft` 结构

## 6. 前端设计

### 6.1 现状问题

当前 `frontend/src/pages/questions/import-utils.ts` 在处理 `docx` 的 `<ol>` / `<ul>` 时，会把每个 `<li>` 输出成：

```text
- 列表项内容
```

这对“作业要求”“简答题分点”是可接受的，但对选择题选项不够，因为它把：

```text
A. 选项一
B. 选项二
```

和：

```text
1. 完成步骤一
2. 完成步骤二
```

都降级成了相同的 `- xxx` 结构。

### 6.2 新的文本抽取策略

前端不再把所有列表统一输出为普通短横线，而是输出带列表语义的中间文本。

目标不是还原完整 Word 样式，而是生成让后端可稳定判断的导入文本。建议规则：

- 段落仍按当前方式输出。
- 有序列表项输出为带列表标记的行。
- 无序列表项输出为带无序标记的行。
- 若 Mammoth/浏览器 DOM 能提供列表类型信息，则一并保留。

推荐中间文本格式：

```text
[OL] 下面关于数据分析说法正确的是（ ）
[OL:A] 数据分析是数学、统计学理论结合科学的统计分析方法
[OL:B] 数据分析是一种数学分析方法
[OL:C] 数据分析是统计学分析方法
[OL:D] 数据分析是大数据分析方法
```

若前端无法拿到字母编号，也至少保留列表身份：

```text
[OL] 选项一
[OL] 选项二
[OL] 选项三
[OL] 选项四
```

无序列表则输出为：

```text
[UL] 提交 PDM 截图
[UL] 提交 MySQL 数据库脚本截图
```

设计意图：

- 后端可以区分“这是列表项”与“这只是普通一行文本”
- 后端可以区分“有序列表候选”与“无序列表候选”
- 即使拿不到 A/B/C/D，也能利用上下文做选择题候选判断

### 6.3 兼容性要求

- 纯文本中的 `A.` / `B.` / `C.` 不应被改写。
- 现有 markdown / pdf 文本导入不需要变更格式。
- 现有图片占位、表格抽取逻辑保持不变。

## 7. 后端设计

### 7.1 显式选项规则保留

当前后端对如下格式的选项识别继续保留，并保持最高优先级：

- `A. xxx`
- `A．xxx`
- `A、xxx`
- `A) xxx`

只要命中显式字母选项，就按现有选择题逻辑处理，不依赖前端新增标记。

### 7.2 新增列表语义识别

`build_import_draft_from_segment` 在识别单题块时，新增对前端列表标记的处理。

分两类：

#### 类型一：显式字母列表

若行形如：

- `[OL:A] xxx`
- `[OL:B] xxx`
- `[OL:C] xxx`

则直接提取为选择题选项，映射成：

- `A -> xxx`
- `B -> xxx`
- `C -> xxx`

这是最稳定的新增路径。

#### 类型二：隐式有序列表

若题目块中连续出现多个 `[OL] xxx`，则只在满足“选择题候选条件”时，把它们顺序映射成 `A/B/C/D...`。

选择题候选条件必须同时尽量保守，避免误判：

- 当前题块的 `type_hint` 指向单选题、多选题、选择题，或
- 题干本身含有明显选择题语义，如“下列说法正确的是”“错误的是”“不属于的是”等，或
- 同题块中已存在字母答案特征（如答案为 `A` / `BC`），并且存在连续有序列表项

满足上述条件后，连续 `[OL]` 列表项按出现顺序映射成 A、B、C、D。

### 7.3 不把普通步骤列表误判为选项

以下情况不能把列表项当成选择题选项：

- 题型是简答题、编程题、论述题，且没有选择题语义
- 作业题或操作题中出现 `1. 提交截图`、`2. 提交脚本` 一类步骤说明
- 无序列表 `[UL]`，除非未来明确扩展支持

也就是说，本次只让 **有序列表 + 选择题候选上下文** 进入隐式选项识别；普通列表继续保留在 `content_text` 中。

### 7.4 内容清洗策略

在构建 `content_text` 时：

- 显式选项行不进入题干
- 被识别为隐式选项的 `[OL]` 行不进入题干
- 未被识别为选项的 `[OL]` / `[UL]` 行，去掉内部标记后保留在题干中

这样可以避免：

- 选择题题干中混入 A/B/C/D 选项文本
- 简答题题干中丢失原本应保留的步骤列表

### 7.5 题型判定协同

`_detect_question_type` 需要接收增强后的选项提取结果。

规则保持：

- 有显式题型提示时，以题型提示优先
- 有 2 个及以上有效选项时，可判定为 `choice`
- 若答案为单字母，倾向单选；若答案为多字母，倾向多选（若当前系统仍统一落 `choice`，则维持现状）

本次不新增新的数据库题型，仅提高现有 `choice` 识别精度。

## 8. 页面图片兜底设计

### 8.1 适用场景

页面图片识别不是默认流程，只在以下场景使用：

- 文本链路返回的草稿中，选择题大量命中“选项不完整”
- 题目边界数量明显异常
- 文本抽取后内容质量过低，无法稳定进入 review
- 用户主动选择“按页面视觉识别”

### 8.2 输入形式

前端把 Word 文档按页转成图片，然后把每页图片作为导入附件发送后端。后端不依赖图片做版面还原，只要求它能基于页面视觉内容识别题目块、题干、选项、答案等。

V1 不要求在浏览器端实现复杂 Word 渲染编辑，只要求能拿到可上传的分页图片。

### 8.3 与文本链路的关系

建议识别流程：

1. 默认先跑文本链路。
2. 若命中 fallback 条件，则提供重新识别入口或自动切换到图片识别。
3. 图片识别产出的结构仍然统一落到 `QuestionImportDraft[]`。
4. review 页面不区分来源，只展示识别结果和问题标签。

### 8.4 范围约束

- V1 不做文本识别结果与图片识别结果的复杂自动融合。
- 一次识别仅采用一条主结果来源：文本或图片。
- V1 允许图片识别只用于 `docx`，不要求同步扩展到所有 `pdf`。

## 9. API 与数据流调整

### 9.1 主路径数据流

`docx` 导入主路径保持不变：

1. 前端读取 `docx`
2. Mammoth 转 HTML
3. 前端把 HTML 转导入文本
4. 前端上传 `rawText + images + tables`
5. 后端分题、识别、返回 `QuestionImportDraft[]`

调整点只在第 3 步：导入文本要保留列表语义。

### 9.2 兜底路径数据流

新增图片识别模式时，数据流为：

1. 前端读取 `docx`
2. 按页转图片
3. 上传页面图片列表
4. 后端按页面视觉内容识别
5. 后端返回 `QuestionImportDraft[]`

返回结构保持一致，避免前端 review 页分叉。

## 10. 错误处理与用户体验

### 10.1 文本链路识别质量提示

若识别结果中大量选择题存在以下问题：

- `选择题选项不完整`
- 实际题目数量明显少于预期
- 多道题只有题干没有选项

系统应明确提示：

- 当前文档可能使用了 Word 自动编号或复杂版式
- 可以尝试“按页面图片重新识别”

### 10.2 review 流程保持统一

无论识别来源如何，仍然进入现有导入校对页，由老师：

- 逐题核对
- 修正题型和选项
- 跳过异常题
- 最终确认导入

这样可以避免新增一套专门的“图片识别结果页”。

## 11. 测试设计

### 11.1 前端测试

补充 `frontend/src/pages/questions/import.test.tsx` 或相关工具测试，覆盖：

- `docx` HTML 中的 A/B/C/D 有序列表被保留为可识别中间文本
- 普通有序步骤列表不会被伪装成显式选项
- 无序列表仍能保留文本内容
- 现有纯文本段落、图片、表格抽取不回归

### 11.2 后端测试

补充 `backend/tests/test_question_import_document_recognize.py`，覆盖：

- 教师样例中的连续单选题能正确识别出 4 道选择题及各自 A/B/C/D 选项
- 显式 `A.` / `B.` 选项题目继续正常识别
- `[OL]` 列表在选择题上下文中可映射成 A/B/C/D
- `[OL]` 列表在作业题、简答题上下文中不会误识别为选项
- 命中 fallback 条件时，后端能返回适合前端提示重新识别的质量信号

### 11.3 手工验证

至少验证三类真实文档：

1. 纯文本 A/B/C/D 题库文档
2. Word 自动编号的选择题文档
3. 含步骤列表的作业题或简答题文档

验收标准：

- 选择题选项不再系统性丢失
- 普通步骤列表不会大面积误判成选择题
- 识别异常时，用户能明确切换到页面图片识别

## 12. 实施顺序

建议分两阶段实施：

### 第一阶段：修主路径

- 前端保留列表语义
- 后端识别列表选项
- 补齐回归测试
- 在现有 review 流程中验证教师样例

### 第二阶段：加兜底

- 新增 Word 分页图片识别入口
- 定义 fallback 触发条件
- 让图片识别结果接入现有 review 页

第一阶段解决当前最痛的问题；第二阶段提升复杂版式文档的成功率。

## 13. 预期结果

完成后，系统应具备以下行为：

- 对普通 `docx` 题库，默认文本识别即可正确识别题干与选项
- 对 Word 自动编号的选择题，选项不再因为列表语义丢失而消失
- 对作业题、简答题中的步骤列表，不会错误转成选择题选项
- 对复杂版式文档，系统能提供页面图片识别作为明确兜底方案
- 所有识别结果继续通过人工审核后再导入题库
