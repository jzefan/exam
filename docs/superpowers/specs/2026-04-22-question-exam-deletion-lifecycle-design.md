# 题目与考试删除生命周期设计

## 背景

当前系统已经大量使用软删除字段 `deleted_at`，但“题目删除”和“考试删除”的生命周期规则并不完整：

- 题目删除目前仅执行软删除
- 考试删除目前也仅执行软删除
- 但模型层的若干外键仍带有 `ondelete="CASCADE"`
- 一旦未来引入硬删除，如果规则不清，会误删：
  - 考生答题记录
  - 提交历史
  - 评分结果
  - 错题记录

同时，当前这次代码题模式改造里，用户希望删除旧代码题并重建测试题，但该题已经被考试引用，因此必须先明确删除策略。

## 目标

- 明确题目与考试的软删除 / 硬删除边界
- 确保已有考生作答历史不会因为后台删除操作而丢失
- 支持“未真正使用过的数据”在合适条件下被彻底清理
- 为后续代码题重建、考试归档、题库整理提供稳定的数据生命周期规则

## 非目标

- 本阶段不重做整套历史快照模型
- 本阶段不实现复杂的归档仓库或冷存储
- 本阶段不允许管理员绕过规则强制清空已有考生历史

## 现状风险

当前模型存在以下级联风险：

- `exam_questions.question_id -> questions.id` 使用 `ondelete="CASCADE"`
- `student_exam_answers.question_id -> questions.id` 使用 `ondelete="CASCADE"`
- `student_exam_submission_answers.question_id -> questions.id` 使用 `ondelete="CASCADE"`
- `student_exam_answers.exam_id -> exams.id` 使用 `ondelete="CASCADE"`
- `student_exam_submissions.exam_id -> exams.id` 使用 `ondelete="CASCADE"`
- `student_exam_submission_answers.exam_id -> exams.id` 使用 `ondelete="CASCADE"`

这意味着：

- 如果题目被硬删除，历史答卷可能被一起删除
- 如果考试被硬删除，学生答题、提交历史、评分结果也可能被一起删除

因此，硬删除必须受到更严格的业务规则约束。

## 方案对比

### 方案 A：题目与考试永远只软删除

优点：

- 最安全
- 永远不会误删历史记录

缺点：

- 无法清理从未真正使用过的脏数据
- 长期会积累大量不可见但永久存在的数据

### 方案 B：是否存在历史作答，决定是否允许硬删除

题目：

- 默认删除先软删除
- 只有在“没有任何活跃考试引用，且没有任何学生历史作答/提交快照引用”时，才允许硬删除

考试：

- 如果没有任何学生开始/提交记录，可以硬删除
- 一旦有学生提交过，则只能软删除

优点：

- 兼顾安全与数据清理能力
- 符合当前产品阶段

缺点：

- 需要补一层引用检查逻辑
- 删除行为不再是单一步骤

### 方案 C：历史快照彻底脱离题目与考试，再允许更积极硬删除

优点：

- 后期数据生命周期最干净

缺点：

- 改动很大
- 牵涉结果页、错题本、教师查看记录等多个链路

## 结论

采用方案 B。

## 删除规则设计

### 1. 题目删除规则

题目删除入口默认执行软删除：

- 设置 `questions.deleted_at`
- 前台题库列表不再展示
- 已引用该题的考试历史仍保持完整

题目允许硬删除的前提必须全部满足：

1. 题目已处于软删除状态
2. 没有任何未删除考试或练习仍引用该题
3. 没有任何学生历史作答记录引用该题
   - `student_exam_answers`
   - `student_exam_submission_answers`
   - `student_question_progress`
   - 未来新增的历史分析表

只要有任一历史引用存在，该题就永久保留为软删除状态，不做硬删除。

这意味着：

- “所有引用它的考试都删了” 只是必要条件，不是充分条件
- 只要学生曾作答过，该题就不能硬删

### 2. 考试删除规则

考试删除分两种情况：

#### 情况 A：没有任何学生开始或提交记录

满足以下条件时允许硬删除：

- 没有 `exam_students.started_at`
- 没有 `exam_students.submitted_at`
- 没有 `student_exam_answers`
- 没有 `student_exam_submissions`

这类考试可以视为“从未真正使用”，允许彻底删除。

#### 情况 B：已有学生提交过

一旦存在任一考生提交记录，该考试默认只允许软删除：

- 设置 `exams.deleted_at`
- 考试不再在正常列表中展示
- 学生答题记录、提交历史、评分结果、反馈记录全部保留

这是本设计中最重要的审计规则：

- **有考生提交过的考试，默认只做软删除**

### 3. 题目硬删除的触发时机

本阶段不在“删除考试”时即时联动硬删题目。

改为采用更稳的判定方式：

- 当题目被软删除后，系统在以下时机检查是否可硬删：
  - 删除考试后
  - 删除练习后
  - 后台执行清理任务时

检查通过才真正硬删。

这样可以避免因为某一次局部删除就误判“该题已无人使用”。

## 推荐实现方式

### 后端

- 为题目增加“是否可硬删”的判定函数
- 为考试增加“是否可硬删”的判定函数
- 删除考试接口改为：
  - 先判断是否存在学生历史
  - 无历史则硬删
  - 有提交历史则软删
- 删除题目接口保持软删
- 增加题目清理函数：
  - 仅清理已软删且已无任何业务引用和历史引用的题目

### 前端

- 题目删除文案增加提示：
  - 已被考试使用的题目将进入回收状态，不会立即彻底删除
- 考试删除文案增加提示：
  - 若已有考生提交，将仅归档隐藏，不会清空答卷历史

## 数据保留原则

本设计采纳以下数据保留原则：

- 考生作答历史优先于后台整理便利
- 一旦出现真实学生提交，相关考试视为审计数据
- 一旦题目进入真实作答历史，也不再允许物理删除

## 测试策略

需要覆盖以下用例：

1. 未被引用题目删除后仅软删
2. 软删题目在无考试引用、无历史答卷时可被硬删
3. 软删题目在有学生答卷历史时不可硬删
4. 无学生历史的考试删除时被硬删
5. 有学生提交历史的考试删除时仅软删
6. 删除考试后，如题目仍被其它未删除考试引用，不可硬删
7. 删除考试后，如题目没有活跃考试引用但仍有学生历史，不可硬删

## 与当前代码题改造的关系

当前旧代码题因为已被考试引用，因此不应直接硬删。

正确做法是：

1. 先按题目删除规则执行软删除
2. 重建一条新的测试代码题
3. 后续由题目清理逻辑判断旧题是否永远保留软删除状态，或在满足条件后再硬删除
