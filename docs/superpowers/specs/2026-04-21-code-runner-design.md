# 编程题在线运行设计

## 背景

当前学生端编程题页面已经具备 Monaco 编辑器、多语言切换、示例测试与自定义输入面板，但“运行代码”按钮仍然只是保存当前输入并展示占位提示，不会真正执行代码。

这会带来两个明显问题：

1. 学生无法在考试中验证代码行为，编程题作答体验不完整。
2. 前端已经暴露了“运行代码”心智模型，但后端没有对应执行能力，容易造成误解。

本次设计目标是在不破坏现有考试作答与交卷评分链路的前提下，为学生端编程题增加“在线运行”能力。

## 目标

### 功能目标

- 支持学生在编程题中点击“运行代码”后真正执行代码。
- 支持 6 种语言：Python、Java、C、C++、JavaScript、Go。
- 支持两类运行模式：
  - 平台预置示例测试
  - 学生自定义输入
- 示例测试返回逐例通过情况。
- 自定义输入返回程序输出与错误信息，但不做通过/失败判定。

### 非目标

- 不将运行结果直接写入最终考试得分。
- 不在第一版支持隐藏测试用例正式判分。
- 不支持联网、依赖安装、多文件工程或交互式程序。
- 不把在线运行与现有主观题 AI 评分流程混合。

## 用户视角行为

### 示例测试

学生在编程题页面选择语言并编写代码后，点击“运行代码”：

- 系统执行该题配置的公开示例测试。
- 结果区展示总状态、总耗时、通过数量。
- 每个测试用例展示输入、期望输出、实际输出、状态。

### 自定义输入

学生切换到“自定义测试”，输入自定义 stdin 内容后点击“运行代码”：

- 系统执行当前代码并把自定义输入传入标准输入。
- 结果区展示输出、错误信息、耗时。
- 不展示“通过/失败”，因为没有标准答案。

### 与考试答案的关系

- 自动保存仍只保存学生答案本身。
- 在线运行结果仅作为即时调试反馈。
- 运行结果不直接影响交卷分数。

## 方案选择

评估过三种方向：

1. 直接在主后端进程内裸跑子进程
2. 在考试系统后端内新增独立代码执行服务层
3. 单独拆分外部判题服务

选择方案 2。

原因：

- 比方案 1 更安全，职责更清晰。
- 比方案 3 更轻量，适合当前阶段快速落地。
- 后续若要扩展为正式编程判题，可在该服务层继续演进，不会推翻前端与路由接口。

## 总体架构

系统拆分为三层：

### 1. 学生考试路由层

放在学生考试接口下，负责：

- 身份校验
- 考试状态校验
- 题目归属校验
- 请求体校验
- 调用代码执行服务
- 返回统一运行结果

建议新增接口：

`POST /api/student/exams/{exam_id}/questions/{question_id}/run`

### 2. 代码执行服务层

新增模块：`backend/src/app/code_runner/`

职责：

- 根据语言与题目配置组装执行任务
- 创建独立临时工作目录
- 写入源码文件
- 编译或执行代码
- 管理超时、输出截断、错误归一化
- 将执行结果转换为统一响应结构

### 3. 前端编程题工作区

继续使用现有 `CodeQuestion` 组件，不重做整体页面结构，只增强：

- “运行代码”异步调用
- 运行中状态
- 结果区真实展示
- 错误与通过情况展示

## 后端接口设计

### 请求

```json
{
  "language": "python",
  "code": "print('hello')",
  "mode": "sample",
  "custom_input": "",
  "sample_case_index": null
}
```

字段说明：

- `language`：当前运行语言
- `code`：当前代码
- `mode`：`sample` 或 `custom`
- `custom_input`：自定义输入；仅在 `custom` 模式使用
- `sample_case_index`：预留字段；第一版可以不启用单例运行，默认执行全部公开示例

### 响应

```json
{
  "status": "failed",
  "mode": "sample",
  "language": "python",
  "stdout": "",
  "stderr": "",
  "compile_output": "",
  "time_ms": 126,
  "memory_kb": 0,
  "case_count": 2,
  "passed_count": 1,
  "cases": [
    {
      "name": "示例 1",
      "input": "1 2",
      "expected_output": "3",
      "actual_output": "3",
      "status": "passed",
      "time_ms": 30,
      "memory_kb": 0,
      "message": ""
    }
  ]
}
```

顶层状态建议统一为：

- `passed`
- `failed`
- `compile_error`
- `runtime_error`
- `timeout`
- `system_error`

### 路由层校验规则

接口调用前必须满足：

- 当前用户是该考试的学生本人
- 考试仍处于允许作答的时间窗口
- 题目属于当前考试
- 题型为 `code`
- 学生仍处于可作答状态

如果不满足，接口返回明确、可翻译的中文错误信息。

## 编程题数据约束

第一版沿用现有题目内容中的 `sample_tests`，并明确其结构：

```json
[
  {
    "name": "示例 1",
    "input": "1 2",
    "expected_output": "3",
    "is_public": true
  }
]
```

设计约束：

- `sample` 模式仅运行 `is_public = true` 的测试用例
- `custom` 模式不使用标准答案比对
- 第一版只支持单文件、标准输入/输出型题目

## 代码执行服务设计

### 目录结构建议

```text
backend/src/app/code_runner/
  __init__.py
  schemas.py
  service.py
  executors.py
  compare.py
  limits.py
```

### 核心职责拆分

- `schemas.py`
  - 运行请求与结果模型
- `service.py`
  - 面向业务层的统一入口
- `executors.py`
  - 各语言编译/运行命令组装
- `compare.py`
  - 示例输出比对规则
- `limits.py`
  - 超时、输出长度等限制常量

### 语言执行策略

- Python：`python3 main.py`
- JavaScript：`node main.js`
- Java：`javac Solution.java` 后 `java Solution`
- C：`gcc main.c -O2 -o main` 后执行
- C++：`g++ main.cpp -O2 -std=c++17 -o main` 后执行
- Go：`go build` 后执行

### 执行隔离与资源限制

第一版至少做到：

- 每次运行使用独立临时目录
- 编译阶段超时，例如 8 秒
- 运行阶段超时，例如 3 秒
- 限制 stdout/stderr 总大小，例如 64KB 到 128KB
- 运行结束即清理工作目录
- 不开放网络
- 不允许额外依赖安装

### 结果归一化

执行层统一输出：

- 编译输出
- 标准输出
- 标准错误
- 退出码
- 是否超时
- 单次或逐例耗时

再由服务层映射为前端可直接消费的 `status` 与 `cases`。

## 前端交互设计

### 工具栏

保留现有布局，仅增强行为：

- 点击“运行代码”发起异步请求
- 请求中按钮进入 loading 态
- 请求中禁用重复点击
- 请求中禁用语言切换，避免结果和代码状态错位

### 示例测试模式

运行完成后，右侧结果区展示：

- 总体状态
- 总耗时
- 通过数量
- 逐例详情

### 自定义测试模式

运行完成后展示：

- 本次输入
- 程序输出
- 错误输出
- 超时或运行异常说明

### 错误反馈

前端需要把技术错误翻译成考生能理解的提示：

- `compile_error` → 编译失败，请检查语法
- `runtime_error` → 运行出错，请检查程序逻辑
- `timeout` → 运行超时，请检查是否存在死循环或复杂度过高
- `system_error` → 在线运行暂时不可用，请稍后重试

## 与现有考试流程的边界

### 保持不变

- 自动保存答案
- 切题自动保存
- 交卷流程
- 客观题自动评分
- 主观题 AI 评分

### 新增但独立

- 编程题在线运行接口
- 编程题运行结果展示
- 编程题运行日志

结论：在线运行是考试过程中的调试辅助能力，不直接改变现有提交与评分链路。

## 审计与观测

第一版至少记录轻量运行日志，字段建议包括：

- `exam_id`
- `question_id`
- `student_id`
- `language`
- `mode`
- `status`
- `time_ms`
- `created_at`

用途：

- 排查学生反馈的运行失败问题
- 观察语言与题目维度的失败分布
- 后续分析学生编程题调试行为

日志落地形式可以是单独表，也可以先统一打结构化日志；若二选一，优先单独表，便于后续分析。

## 测试策略

### 后端

- 单元测试
  - 命令组装
  - 输出比对
  - 状态映射
- 服务测试
  - 编译成功
  - 编译失败
  - 运行错误
  - 超时
  - 示例通过
  - 示例失败
- 路由测试
  - 权限校验
  - 考试时间校验
  - 非编程题拒绝运行

### 前端

- 运行中按钮状态
- 示例测试结果渲染
- 自定义测试结果渲染
- 编译错误与超时提示
- 语言切换禁用与恢复

## 风险与后续演进

### 已知风险

- 本地受限子进程隔离度弱于专业沙箱产品
- 六种语言的运行环境需要部署机具备对应运行时
- 编程题题目结构需要更严格地规范示例测试配置

### 后续演进方向

- 隐藏测试用例与正式编程判题
- 运行历史记录与运行次数分析
- 更强隔离的独立执行服务
- 编程题最终得分与判题结果联动

## 决策摘要

本次采用“学生考试路由 + 独立代码执行服务层”的方案，为编程题提供在线运行能力。

第一版覆盖：

- 6 种语言
- 平台示例测试
- 学生自定义输入
- 统一结果结构
- 受限执行与基础审计

同时明确不把运行结果直接计入最终得分，以确保考试评分链路保持稳定、可解释、可渐进演进。
